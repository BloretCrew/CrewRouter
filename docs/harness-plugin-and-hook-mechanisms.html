2.3 Hook 系统（问题 3）：事件最全的一套，四种 hook 形态，退出码 + JSON 双通道决策

Hook 点位（事件全集）

SDK 导出的完整事件表（src/entrypoints/sdk/coreTypes.ts:25-44 HOOK_EVENTS）：PreToolUse、PostToolUse、PostToolUseFailure、Notification、UserPromptSubmit、SessionStart/SessionEnd、Stop/StopFailure、SubagentStart/SubagentStop、PreCompact/PostCompact、PermissionRequest/PermissionDenied、Setup、TeammateIdle、TaskCreated/TaskCompleted。settings 校验层接受的键与之基本一致（src/utils/settings/settings.ts:594-608）。插件侧 matcher 表还多出内部事件：Elicitation、ElicitationResult、ConfigChange、WorktreeCreate/WorktreeRemove、InstructionsLoaded、CwdChanged、FileChanged（loadPluginHooks.ts:27-58）。

配置位置

settings.json 的 hooks 字段（用户级/项目级/本地级多层 settings 合并），结构为 { 事件名: [{ matcher, hooks: [...] }] }；UI 管理入口 /hooks（src/components/hooks/HooksConfigMenu.tsx），配置快照与变更检测见 hooksConfigSnapshot.ts / hooksConfigManager.ts。

四种 hook 形态（不止 shell 命令一种！）

  • command：shell 命令，字段含 timeout/statusMessage/once（执行一次后移除）/async（后台不阻塞）/asyncRewake(后台且 exit 2 时唤醒模型)（src/schemas/hooks.ts:31-64）。
  • prompt：交给 LLM 评估的 prompt，支持 $ARGUMENTS 占位符与指定 model（schemas/hooks.ts:62-91）——相当于内置「LLM-as-judge」钩子。
  • http：POST JSON 到 URL，headers 支持显式白名单的环境变量插值（allowedEnvVars）（schemas/hooks.ts:93-121），SSRF 防护见 src/utils/hooks/ssrfGuard.ts。
  • agent：由子代理执行的 hook（执行器 src/utils/hooks/execAgentHook.ts；另见 execPromptHook.ts/execHttpHook.ts）。

所有形态共享 if 字段：用权限规则语法（如 "Bash(git *)"）预过滤，避免为不匹配的工具调用白白 spawn 进程（schemas/hooks.ts:17-24）。

2.4 与 MCP 的关系（问题 4）：两套机制，插件可作为 MCP 的「打包外壳」

  • 独立配置面：MCP server 可不经插件直接配置——项目根 .mcp.json（需用户逐个批准/拒绝，src/utils/settings/types.ts:406 approvedMcpServers 字段；main.tsx:3953 提供 mcp reset-project-choices 重置审批），或 claude mcp add CLI（main.tsx:3924-3930）。
  • 插件内嵌 MCP：插件清单含 PluginManifestMcpServerSchema（schemas.ts:893），插件可直接自带 MCP server；甚至支持 MCPB/DXT 桌面扩展包格式——下载、解压、把 DXT manifest 转成 MCP 配置，并支持「需用户配置」状态机与 per-plugin 存储变量替换（src/utils/plugins/mcpPluginIntegration.ts:30-70、pluginOptionsStorage.ts）。
  • 共存命名空间：main.tsx:2791 注释明确区分 plugin:* 键与手工 .mcp.json 条目——两来源在同一 server 注册表中以命名空间并存。

定位结论：MCP 是「工具供给协议」，Plugins 是「分发与生命周期框架」；插件把 commands/agents/skills/hooks/MCP servers 打成一个可版本化、可市场分发的单元。二者正交且可嵌套。

2.5 沙箱与权限模型（问题 5）：声明式组件零代码执行，hook 全权运行，靠准入治理兜底

成分运行方式隔离手段
插件本体（commands/agents/skills/output styles）Markdown/JSON 声明文件，由主进程解析吸收，不含可执行代码天然无需沙箱；风险在提示内容而非代码
Hooks（command 型）spawn shell 进程，以用户完整权限运行无内置隔离（推测：官方立场是 settings 属于用户本机信任域）；治理靠企业管理 managedPlugins.ts/pluginPolicy.ts/pluginBlocklist.ts 准入控制
Hooks（http 型）主进程外发 HTTP POSTSSRF 防护（src/utils/hooks/ssrfGuard.ts）+ header 环境变量插值须显式 allowedEnvVars 白名单（schemas/hooks.ts:106-119）
Bash 工具沙箱设置OS 级沙箱（network/filesystem/excludedCommands 等键，settings.ts:579-591）注意：这是约束模型的 Bash 工具的，并非约束 hooks 本身
PreToolUse hook 决策权可返回 allow/deny/ask 直接参与权限判定（utils/hooks.ts:345）hook 即权威，因此 hook 配置本身的写入权就是最高权限

小结：Claude Code 的安全模型是「配置即信任」——能写你 settings.json/hooks 的东西就能全权执行命令；它选择的防线是分发侧治理（官方市场校验、仿冒名拦截、blocklist、企业策略）而非运行时沙箱。

2.6 与 CrewRouter 插件系统的对比借鉴（问题 6）

CrewRouter 现状参照：server/plugins/host.js:8-17（vm 沙箱 + permissions 数组：storage/network/gateway:modify/pages:register/routes:register/provider:register/apikey:modify/billing:modify/cron:register）、server/plugins/host.js:24-29 网关钩子五件套（gateway:requestReceived/beforeUpstream/upstreamResponse/responseChunk/finalResponse）、server/plugins/hooks.js:9 钩子管线（payload 原地改/返回替换、priority 排序、熔断摘除、零订阅者旁路）。

值得借鉴的设计

  1. 权威阻断 + 理由回灌闭环：Claude Code 的 PreToolUse deny 不是「记录一下」，而是替权限系统做决定，且阻断原因会作为 feedback 回到模型上下文让它自我修正；PostToolUse 更有 preventContinuation 硬终止（toolHooks.ts:113-130）。对照我们的 gateway:requestReceived 目前只能改 payload：建议引入显式 {action:'block', reason} 决策，reason 可选择回注为对客户端可见的错误体或对上游的替代请求。
  2. Hook 多形态（尤其 prompt/http 型）：LLM-as-judge 的 prompt hook（schemas/hooks.ts:62-91）意味着「策略检查」不必写代码，一段 prompt 就是一个合规审查器；http hook 则让外部审计服务零侵入接入。我们可在网关钩子旁增加 {type:'prompt'}/{type:'http'} 的轻量 hook 声明通道（跑在 host 侧、受同一权限门控）。
  3. 预过滤 if 条件：用规则语法（"Bash(git *)"）在 spawn 前过滤（schemas/hooks.ts:17-24），与我们 hasSubscribers() 零开销旁路同思路但更细——可下放到 payload 维度（如仅当 provider/model 匹配才进入管线）。
  4. once/async/asyncRewake：后台化 hook + 完成后唤醒（utils/hooks.ts:202-212）对网关场景的映射是「响应结束后异步任务再主动推送/记账」，适合计费调整、事后审计类插件。
  5. additionalContext/systemMessage 注入：hook 可向模型上下文注入文本——对应到我们，可让 beforeUpstream 支持声明式追加 system prompt 片段，而不仅是改写现有字段。
  6. manifest 即文档的能力面声明：一张清单列全 commands/agents/skills/hooks/mcpServers/lspServers/settings/userConfig（schemas.ts:884-898），安装前即可静态审查插件能干什么。我们的 plugin.json 已有 permissions 数组，方向一致；可补「声明式组件段」（如页面插槽之外的 cron 已有），并让商店展示能力摘要。

我们已有、Claude Code 反而没有的

运行时硬隔离：vm 沙箱 + 每钩子 2s 超时 + ctx.fetch 10s 超时 + SSRF 校验 + 连续错误熔断自动摘除（host.js:41-46、hooks.js:11-14）——Claude Code 的 shell hook 完全没有这些。我们的弱点是插件必须写成 JS 模块、门槛高于「一行命令一个 hook」；上述第 2 点的多形态声明正好补这个短板。

3.4 与 MCP 的关系（问题 4）：MCP 三重身份——能力源、hook 执行器、可打包资产

  • 独立配置面：MCP server 可独立于插件配置（core/src/connectors.rs 连接器体系）。
  • 插件内嵌：manifest 的 mcp_servers 段让插件自带 MCP 能力（plugin/src/manifest.rs:29-35）；apps 类资源配合 MCP 路由（app_mcp_routing.rs）。
  • hook 执行载体：HookHandlerType::McpTool（protocol.rs:1528）+ 专门的 hooks/src/engine/mcp_runner.rs（含 HookMcpExecutor，engine/mod.rs:25）——hook 处理逻辑可以部署成 MCP tool，由远端服务承担。

定位结论：Codex 把 MCP 从「工具供给」进一步升格为「hook 计算载体」，插件则是把这些资产打包分发的容器。三者正交、互相嵌套。

3.5 沙箱与权限模型（问题 5）：无代码沙箱，但有显式 Hook 信任状态机 + 环境变量清洗

机制说明证据
Hook 信任状态机每个 hook handler 带 HookTrustStatus；配置层提供 bypass_hook_trust 开关；TOML 与 JSON 来源的 hook 收敛到同一信任身份，避免「换个文件就绕过审批」engine/mod.rs:33、registry.rs:43、discovery.rs:744

3.6 与 CrewRouter 插件系统的对比借鉴（问题 6）

值得借鉴的设计

  1. updated_input 结构化改写通道：Codex 把「hook 改写入参」做成显式字段而非整体 payload 替换。我们的 gateway:beforeUpstream/gateway:requestReceived 目前靠「返回非 undefined 对象即视为替换整个 payload」（server/plugins/hooks.js:9 约定）——建议约定合并语义（浅合并或字段级 diff），降低插件误覆盖整包的风险。
  2. Hook 信任状态机：per-hook trust 审批 + 跨配置源收敛信任身份（discovery.rs:744）。我们的 vm 沙箱在运行时已隔离，但「新装插件的钩子在首次生效前需人工确认」这层产品流程仍可借鉴，尤其针对从商店批量安装的场景。
  3. MCP 作为 hook 执行器：McpTool 形态意味着重策略（内容审核、合规检查）可以外置为服务。我们网关侧可考虑允许 hook handler 声明为 {type:'mcp', server, tool}，host 代为调用——天然获得异步化与横向扩容。
  4. 市场运营元数据：安装策略三态 + 鉴权时机两态（marketplace.rs:157-182）+ interface 展示段（capabilities/default_prompt/logo）。我们的插件商店统计上报可吸收这套字段。
  5. 行业信号：引擎直接命名 ClaudeHooksEngine 说明 Claude Code 的 hook wire format 已是事实标准。CrewRouter 若做「多 harness 兼容钩子层」，对齐 CC/Codex 的事件名 + 输入输出 JSON 结构是最省力的互操作路径——我们的网关本来就转发这两家流量。

我们已有、Codex 没有的

4. OpenCode（进程内 JS 插件 + output 原地改写的事件总线）

4.4 与 MCP 的关系（问题 4）：完全独立的两套体系，靠 event 总线松耦合

  • MCP 独立配置：opencode.json 的 mcp 字段，分 type:"local"（stdio 子进程）与 type:"remote"（HTTP/SSE）两类，带 OAuth 支持（src/mcp/index.ts:238/:342/:379-380、oauth-provider.ts）。
  • 插件不承载 MCP：插件清单里没有 mcpServers 段；插件想碰 MCP 只能通过通用 event hook 监听事件或在 tool.execute.* 中改写。反之 MCP 工具进入 tool.execute.before/after 管线时与内建工具一视同仁（tools.ts:107 对所有 item 生效）。
  • 对比：Claude Code/Codex 是「插件可以打包 MCP」；OpenCode 是「插件与 MCP 互不嵌套、平行存在」。

4.5 沙箱与权限模型（问题 5）：无任何隔离——进程内全权代码

这是三个 harness 中权限模型最激进的：插件是动态 import 进主进程的 JS 模块，拥有完整 Node.js 能力（任意 fs/net/child_process），无沙箱、无权限声明、无审批流。loader 的防线只有两个工程性检查：checkPluginCompatibility 版本兼容校验与安装失败重试分类（loader.ts:9-11、:70-73）。npm 安装来源意味着供应链风险面等同于直接装 npm 包。

对比结论：Claude Code「配置即信任」（hook=全权 shell），Codex 加了信任状态机，OpenCode 干脆「代码即信任」。三者都没有运行时能力收敛——CrewRouter 的 vm 沙箱 + permissions 数组在业界属少数派。

4.6 与 CrewRouter 插件系统的对比借鉴（问题 6）

值得借鉴的设计

  1. 统一 hook 签名 + output 原地改写：OpenCode 用一个泛型 trigger(name, input, output) 约束全部事件，插件心智模型极简（拿到 output 改就是了）。我们的钩子管线已是 (payload, meta) => payload|undefined（server/plugins/hooks.js:9-10），语义同源；可进一步把「原地修改 vs 返回替换 vs 返回决策对象」三种返回形态写成正式协议文档并做 schema 校验。
  2. chat.headers / system prompt 重写位：这两个 hook 点对我们网关场景极具吸引力——chat.headers 对应我们转发上游时的 header 注入需求，experimental.chat.system.transform 对应 system prompt 改写需求。建议在 gateway:beforeUpstream 旁增设更细粒度的声明式点位：upstream:headers、prompt:systemTransform。
  3. npm 分发 + 兼容性检查流水线：loader 的 Plan→Resolved→Loaded 三阶段 + retryable 错误分类（loader.ts:19-33、:70-73）比我们目前本地目录加载更工程化；商店安装可复用该思路（下载→兼容检查→签名校验→落盘）。
  4. 全局事件总线兜底：event(input) 让插件能旁听一切内部事件而不必为每种事件单开 hook——适合审计类插件低成本接入。我们的钩子总线可加一个 *:afterAll 通配订阅位。

反面教材（我们要避开的）

无隔离的进程内插件 = 一个恶意/劣质 npm 包即可窃取所有 API key 与会话数据。CrewRouter 的 vm 沙箱 + 显式 permission 声明正是对这个模型的修正，应坚持而非向其看齐。

// grok-build/crates/codegen/xai-grok-agent/src/plugins/trust.rs:1-16（模块文档原文）

5.6 与 CrewRouter 插件系统的对比借鉴（问题 6）

值得借鉴的设计

  1. Blocked ≠ Failed + 显式 fail-open：把「hook 阻断」和「hook 自己挂了」分成两个结果类型，失败策略明文写死 fail-open（result.rs:63 注释）。我们的钩子管线有熔断（连续 5 错摘除，hooks.js:11-14），本质也是 fail-open，但未在协议层区分「决策性阻断」与「故障」——建议在 apply() 返回值中显式分型，避免插件把异常当阻断用。
  2. force_stop 覆盖 block 的三方门控：Stop 门控里用户级强停优先于插件阻断（result.rs:11）。映射到我们：gateway:requestReceived 若引入 block 决策，应同时定义管理员级 override，防止插件阻断把网关变成单点故障。
  3. 零清单约定发现：没有 plugin.json 也能靠目录约定工作，降低最小插件的门槛。我们的 plugin.json 是强制的（host.js validateManifest），可考虑「只有 frontend/ 目录的纯 UI 插件免清单」的轻量通道。
  4. 路径逃逸剔除：声明资源解析后拒绝 .. 出根并告警（manifest.rs:52-70）。我们 vm 沙箱内风险较低，但插件声明的页面/静态资源路径校验可补同类检查。
  5. Claude 兼容布局作为分发策略：同时认 .claude-plugin/、.claude/plugins/ 意味着 Claude 插件生态可直接平移。CrewRouter 商店若想冷启动内容量，「兼容导入 Claude/Codex 插件包中的 hooks+skills 声明」是低成本路径。

我们已有、Grok Build 没有的

vm 运行时沙箱、权限数组、钩子超时熔断依旧独有；Grok Build 的信任模型管的是「要不要让你跑」，我们管的是「跑了能碰什么」——两层互补。

Claude 全部事件都有对应物之外，还加了 PostToolUseFailure / PostToolBatch / MessageDisplay / StopFailure / SessionDelete / PermissionDenied / TodoCreated / TodoCompleted / InstructionsLoaded / UserPromptExpansion 十个自有点位——事件面是目前所有 harness 中最宽的。

四种执行形态（其他 harness 最多两种）

  • command：spawn 子进程，默认 60s 超时、输出截断 1MB（hookRunner.ts:42-49），环境经 sanitizeChildEnv 清洗后继承（hookRunner.ts:31）；支持异步注册表模式（asyncHookRegistry.ts，长跑 hook 不阻塞回合）。
  • http：httpHookRunner.ts 直发 HTTP 端点，配套 ssrfGuard.ts + urlValidator.ts 做 SSRF 防护——把「hook 打内网」当一等威胁建模，各家仅此一家。
  • function：进程内函数 hook（functionHookRunner.ts），仅限 session hooks 场景使用（types.ts:155 注释「Session Hook specific」）。
  • prompt：promptHookRunner.ts——把 hook 输入 JSON 塞进 prompt 模板发给 LLM 做单轮判定，可用 model 字段覆盖当前会话模型（types.ts:183-200）。用 LLM 当策略引擎是独有的设计。

配置来源四级合并

hook 注册表从 session / user / project / extension 四级来源收集并合并（hookRegistry.ts:58 注释、:269-273 扫描激活扩展的 hooks 字段）。

6.4 与 MCP 的关系（问题 4）：mcpServers 是扩展清单的一等字段

  • MCP server 定义直接内嵌扩展清单（starter 示例即带 mcpServers.nodeServer），安装扩展 = 注册其 MCP servers；server 本体仍是独立子进程（command: node dist/example.js），扩展只是打包分发外壳——与 Claude/Grok 的「插件包 MCP」定位一致。
  • 反向还有 claudeMcpImport.ts：把用户已有的 Claude MCP 配置导入 Qwen，降低迁移成本。
  • hooks 与 MCP 相互独立又可组合：hook 可以是 http 形态直接打一个 MCP 化的服务端点，但协议层互不依赖。

6.5 沙箱与权限模型（问题 5）：无 OS 隔离，靠「清洗 + 校验 + 显式信任」三层软防护

  • command/function hook 都在主进程权限域内运行（spawn 子进程继承用户身份），无 OS 级沙箱。
  • 软防护三件套：环境清洗（sanitizeChildEnv，hookRunner.ts:31）、SSRF 校验（http hook 的 ssrfGuard/urlValidator）、归档安全（zip 安装的路径穿越检查，archive-safety.ts / zip-extraction）。
  • 网络侧另有 extension/network-policy.ts 与 redaction.ts（脱敏）——对「扩展能访问什么网络」有显式策略文件的尝试，同类产品少见。
  • 信任粒度精确到单条 hook 命令键（name:command），且按项目路径隔离存储——同一 hook 在 A 项目信任不代表 B 项目信任。

6.6 与 CrewRouter 插件系统的对比借鉴（问题 6）

值得借鉴的设计

  1. HTTP hook + SSRF 防护：若 CrewRouter 插件钩子未来开放 webhook 型执行端点，Qwen 的 ssrfGuard/urlValidator（私网地址黑名单类校验）应作为必选项而非可选加固——网关型产品天然更怕 SSRF。
  2. fail-open 留痕（hookError 字段）：我们钩子管线熔断摘除已是 fail-open，但可借鉴「错误吸收后在结果对象上显式标记」的做法，让 gateway:beforeUpstream 的调用方能在响应元数据里看到「本次未经钩子审计」。
  3. 外来格式转换器冷启动生态：claude/gemini/qoder 三个 converter 证明「兼容导入头部竞品插件包」是可行的生态策略。CrewRouter 商店冷启动可做「Claude 插件包 → CrewRouter 插件」转换器（hooks+skills+agents 声明部分机械映射即可）。
  4. prompt hook（LLM 判定型钩子）：用一次廉价 LLM 单轮调用做策略判定，适合我们的内容审校场景（如 gateway:requestReceived 上挂「判断该请求是否越权」的 LLM 钩子）——成本可控且有 model 字段可指定便宜模型。
  5. 四级配置来源合并：session/user/project/extension 同名 hook 的优先级与去重规则值得我们在多租户场景预研（租户级 vs 实例级钩子冲突时的合并语义）。

我们已有、Qwen 没有的

vm 运行时沙箱与权限数组依旧独有——Qwen 的 function hook 能跑进程内任意代码但仅限会话内使用，恰恰说明「进程内代码 SDK」在没有沙箱时不敢做成分发形态，反证了我们 vm 方案的前瞻性。

7. Hermes（Python 插件目录 + Toolset 分组，装饰器式生命周期回调）

仓库内无完整源码副本 · 置信度：低—中（推测章）· 依据：docs/harness-request-behavior-research.md 相关章节结论 + 公开资料 + Python agent 生态惯例推断

本章未经源码考古验证。「Hermes」在此指研究范围内那款 Python 技术栈的 agent harness；具体 API 名称均为推断表述，不应作为对接实现的依据。

7.1 插件形态（问题 1）

推测：扩展机制是约定目录 + 进程内 import 的 Python 式做法——项目/用户目录下的 plugins/ 文件夹，每个子目录是一个 Python 包（带 __init__.py 或轻量 manifest，如 plugin.yaml 声明名称与入口），harness 启动时扫描、动态导入并调用其注册入口。安装方式即「把目录放进 plugins/」，最多辅以 pip 安装第三方依赖；没有市场/registry 形态的分发。

与之配套的是 toolset 概念：把若干相关工具聚成组（如「文件读写组」「Shell 组」「浏览器组」），插件最常见的产出就是一个自定义 toolset；会话/配置层面可以按 toolset 整体启用或禁用。

7.2 插件 API 面（问题 2）

  • 推测的能力面：① 注册 toolset / 工具函数（带类型签名与 docstring，直接成为模型可见的 tool schema）；② 注册 slash 命令或快捷指令；③ 订阅生命周期钩子（见 7.3）；④ 只读访问会话上下文（历史消息、工作目录、配置）。
  • 与 Claude Code 的「声明式资源捆绑」相反，这类 Python 插件是代码级 SDK：注册时拿到的是宿主对象的内存引用，能做的事上限就是宿主内部 API 的暴露面积——灵活但危险（见 7.5）。
  • 注入 system prompt 的能力大概率以「插件返回一段 system 片段」的形式存在（生态通例），而非独立的 prompt 注册接口。此条为弱推测。

7.3 Hook 系统（问题 3）

推测：hook 以装饰器 / 回调注册表达，而非外部进程。典型点位与 Claude 同构：

@plugin.on_session_start      # 会话建立
@plugin.on_prompt_submit     # 用户输入提交前，可改写 prompt
@plugin.before_tool_call     # 可 deny / 改参数
@plugin.after_tool_call      # 可附加观察结果 / 截断输出
@plugin.on_stop              # 回合结束
  • 输入/输出形态的本质差异：hook 收到的是强类型 Python 对象（引用传递），不是序列化 JSON；返回值通过对象字段影响主流程（deny=True / 替换后的参数 / 附加上下文文本）。省去了跨进程序列化，但也意味着 hook 崩溃可以直接炸掉主进程。
  • 配置位置：推测为项目配置文件中的 hooks 小节 + 插件自带注册二合一，不存在 settings.json 式的集中 hook 清单。

7.4 与 MCP 的关系（问题 4）

推测：MCP 以「一种外部 toolset/provider 类型」的身份接入——配置里声明 stdio/SSE server，其工具被折叠进统一的 toolset 命名空间，与原生插件工具同场竞争。MCP 不是分发外壳（不像 Claude/Qwen 的插件包内嵌 mcpServers），两套机制平行存在。

7.5 沙箱与权限模型（问题 5）

  • 推测：无任何隔离。import 即全权——插件代码与主进程同一解释器、同一用户身份、同一文件系统与网络权限。Python 生态的插件系统几乎全是这个模式（参考 pytest/Jupyter 扩展）。
  • 信任控制至多是「目录白名单 / 首次加载确认」级别的软门槛。

7.6 与 CrewRouter 插件系统的对比借鉴（问题 6）

  1. 引用传递 vs 序列化传递的取舍：Hermes 式进程内强类型上下文开发体验最好，但代价是零隔离、零语言中立。CrewRouter 的钩子走网关边界（必然序列化），正确姿势是把schema 版本化 + 强校验做好，用类型安全弥补拿不到引用的损失。
  2. before_tool_call 的 deny/modify 双语义与我们 gateway:beforeUpstream 的 block/rewrite 诉求完全同构，印证现有设计方向。
  3. 反例价值：「import 即全权」的插件体系在单机个人工具里可容忍，放到多租户网关场景不可接受——这正是 CrewRouter 把 vm 沙箱 + 权限数组做成默认分发前提的差异化依据。

8. OpenClaw（npm 插件 + Plugin SDK + SKILL.md 技能层）

仓库内无完整源码副本 · 置信度：中（架构与机制基于公开文档/README 记忆复述，具体 API 名称可能有出入，均属半推测）

OpenClaw（前身 Clawdbot / Moltbot）是开源的个人 AI 助理/消息网关：常驻 Gateway 守护进程作为唯一控制面（本地 WebSocket/HTTP API），向下挂多个消息渠道（WhatsApp/Telegram/Discord 等）与 agent 运行时。它与 CrewRouter 在「网关为中心」这一点上结构最像，故单独一节。

8.1 插件形态（问题 1）

  • 插件 = npm 包形式的 TypeScript/JS 模块，进程内加载（openclaw plugins install <npm 包|本地路径>），启用清单记录在 ~/.openclaw/openclaw.json 的 plugins.allow / plugins.entries 字段——显式允许名单 + 条目配置两级。
  • 技能（Skills）是独立的第二层：采用 Anthropic 风格的 SKILL.md 目录约定（Markdown 指令包，可带附属脚本），与代码级插件解耦——「行为知识」走技能，「能力接线」走插件。
  • 无中心化市场，分发靠 npm registry 与手工目录拷贝。（分发细节为中低置信度。）

8.2 插件 API 面（问题 2）

推测（基于公开示例归纳）：Plugin SDK 的核心特征是单一插件可同时贡献多种能力类型，由宿主统一装配：

能力类型作用
channel新增一条消息渠道（收发消息的适配器）
tool向 agent 注册可调用工具
provider新增模型/服务提供方
command聊天内命令（如 /status）
hook handler订阅生命周期事件（见 8.3）
cron/定时任务周期性触发 agent 行为

这与 Claude Code「一个清单捆七类组件」的设计殊途同归：聚合式 manifest 是成熟插件的共同形状。

8.3 Hook 系统（问题 3）

  • 推测：事件总线 + 命名空间化事件名（形如 agent:before_tool_call、message:new、session:start），插件在注册时声明感兴趣的事件并给出处理函数；agent:before_tool_call 类事件的处理结果可以拒绝执行该工具调用。
  • 另一族容易混淆的东西是入站 Webhook：OpenClaw 有把外部 HTTP POST 变成一次 agent 触发的特性。注意它是触发器（trigger）而非拦截器（interceptor）——只负责「发起回合」，不在主流程上设卡。
  • hook 的配置随插件条目写在 openclaw.json，无独立的全局 hooks 清单。（事件名与配置字段为记忆复述，精确拼写待核。）

8.4 与 MCP 的关系（问题 4）

推测（置信度偏低）：MCP server 可作为一种工具来源接入（生态大势，各家均已跟进），但 OpenClaw 的主扩展面是自有 Plugin SDK；MCP 在这里是能力供给方之一，不承担分发/打包职能。两套机制的关系是「SDK 管接线、MCP 管供货」。

8.5 沙箱与权限模型（问题 5）

  • 默认信任模型是「单用户本机」：Gateway 只监听本机/内网，远程访问靠设备配对 + token + TLS（官方建议套 Tailscale）。在这个前提下，插件进程内全权运行被认为可接受。
  • 风险集中在 exec 类工具上：提供可选的 Docker 沙箱执行模式，以及工具级 allow/deny 名单——隔离是「按工具开关」而不是「按插件强制」。
  • 对比 CrewRouter：OpenClaw 用部署拓扑（本机 + 配对）替代了运行时隔离，这在多租户产品里不可复制。

8.6 与 CrewRouter 插件系统的对比借鉴（问题 6）

  1. 聚合式插件 manifest：一个插件同时贡献 channel/tool/command/hook 的形状再次验证了我们二期能力面清单的方向；可进一步对齐的是「同一插件内各能力共享一个启用开关与配置命名空间」。
  2. 事件名命名空间化（域:事件）：比裸字符串事件名可读性与可过滤性好，值得在我们的事件枚举里采纳为命名规范。
  3. 触发器与拦截器分家：OpenClaw 明确区分了 inbound trigger 与 interceptor 两类入口。CrewRouter 网关除 gateway:requestReceived 这类拦截点外，可增设入站触发型钩子类别（定时/外部 HTTP 发起一次代理流程），二者不可混用同一配置段。
  4. Skills 与 Plugin 分层：「Markdown 技能管知识、代码插件管接线」的分工干净，且与 Claude 生态兼容——我们的商店如果同时收两种货，应沿用这个界线而不是混在一个类型里。

9. DeepSeek Harness（无公开原生插件机制，评测型运行时）

仓库内无源码副本 · 置信度：低（整章推测）· 依据：公开资料（模型卡/API 文档/评测技术报告）+ 生态惯例

DeepSeek 公开的是模型与 API（OpenAI 兼容端点，另提供 Anthropic 兼容路径供 Claude Code 等客户端直连），并未发布过一款面向终端用户的、有插件市场的 CLI 编码产品。本章把「DeepSeek Harness」理解为其官方评测/agent 运行脚本层进行推断，全部内容仅供横向对比定位。

9.1–9.3 插件形态 / API 面 / Hook 系统（问题 1–3）

  • 推测：三问同答——没有。评测型 harness 的典型形状是一个固定的 agent 循环（构造 system prompt → 模型输出 tool call → 本地执行 → 结果回填 → 再推理直到终止条件），扩展方式就是改源码或 fork，不存在插件清单、hook 清单或配置化拦截点。
  • 「插件 API 面」由 API 层间接提供：OpenAI 兼容 function calling 协议本身决定了客户端可以自由编排工具集——这是协议级扩展性，不是产品级插件机制。

9.4 与 MCP 的关系（问题 4）

推测：模型侧的工具调用训练（V3.x 系列）足以支撑 MCP 客户端接入，社区实践普遍是在客户端壳里挂 MCP server 来给 DeepSeek 模型供货；官方 harness 是否内建 MCP 客户端未见公开说明，判断为「跟进中/视评测需要」。MCP 与其说是它的插件机制，不如说是外部世界给它补插件机制。

9.5 沙箱与权限模型（问题 5）

推测：不适用。评测场景的隔离发生在实例层（SWE-bench 类任务的 Docker 容器），而不是插件层——因为根本没有插件。这恰好提供了一个干净的对照组：当扩展面为零时，安全边界退化为「整个 harness 跑在哪个容器里」。

9.6 与 CrewRouter 插件系统的对比借鉴（问题 6）

  1. 反面参照系：「没有插件机制的 harness」正是 CrewRouter 的价值位——在上游 harness 不可改造的前提下，传输层网关是唯一能注入策略、审计与扩展的位置。我们所有 hook 点（gateway:requestReceived/beforeUpstream）本质上都在补这一层空白。
  2. 双协议兼容的启示：DeepSeek 同时供 OpenAI/Anthropic 兼容端点，让别人的 harness 成为自己的分发渠道。CrewRouter 协议适配层同理：兼容面越宽，可挂钩子的 harness 越多。
