2.1 插件形态（问题 1）：Git 仓库式插件包 + Marketplace 分发

原生机制：Claude Code 有两层独立的原生扩展机制——Plugins（功能打包分发）与 Hooks（生命周期钩子）。插件本质是一个含 .claude-plugin/plugin.json 清单的目录/Git 仓库，可捆绑七类组件。

安装方式

  • Marketplace 分发：市场源支持五种引用方式——直链 URL、GitHub 仓库、任意 Git URL、npm 包、本地路径（src/utils/plugins/schemas.ts:906-912 MarketplaceSourceSchema）。官方市场清单走 GCS 拉取（officialMarketplaceGcs.ts），并有防「仿冒官方市场名」的同形字（homograph）校验（schemas.ts:70-100 BLOCKED_OFFICIAL_NAME_PATTERN、NON_ASCII_PATTERN）。
  • 安装入口：/plugin 交互菜单；无人值守场景走 headlessPluginInstall.ts；企业管理走 managedPlugins.ts + pluginPolicy.ts（策略白名单/黑名单，配套 pluginBlocklist.ts）。
  • 启用状态：记录在 settings 的 enabledPlugins 字段，支持热重载——settings 变更经 settingsChangeDetector 触发重载（src/utils/plugins/loadPluginHooks.ts:18-26）。

2.2 插件 API 面（问题 2）：声明式组件挂载，而非代码级 SDK

Claude Code 插件没有传统意义的运行时代码 API（不提供 JS 模块在主进程内 import 后调用的接口）；它把「插件能做的事」全部表达为声明式的资源捆绑，由宿主装载器逐类吸收进主流程：

2.3 Hook 系统（问题 3）：事件最全的一套，四种 hook 形态，退出码 + JSON 双通道决策

Hook 点位（事件全集）

SDK 导出的完整事件表（src/entrypoints/sdk/coreTypes.ts:25-44 HOOK_EVENTS）：PreToolUse、PostToolUse、PostToolUseFailure、Notification、UserPromptSubmit、SessionStart/SessionEnd、Stop/StopFailure、SubagentStart/SubagentStop、PreCompact/PostCompact、PermissionRequest/PermissionDenied、Setup、TeammateIdle、TaskCreated/TaskCompleted。settings 校验层接受的键与之基本一致（src/utils/settings/settings.ts:594-608）。插件侧 matcher 表还多出内部事件：Elicitation、ElicitationResult、ConfigChange、WorktreeCreate/WorktreeRemove、InstructionsLoaded、CwdChanged、FileChanged（loadPluginHooks.ts:27-58）。

配置位置

settings.json 的 hooks 字段（用户级/项目级/本地级多层 settings 合并），结构为 { 事件名: [{ matcher, hooks: [...] }] }；UI 管理入口 /hooks（src/components/hooks/HooksConfigMenu.tsx），配置快照与变更检测见 hooksConfigSnapshot.ts / hooksConfigManager.ts。

四种 hook 形态（不止 shell 命令一种！）

  • command：shell 命令，字段含 timeout/statusMessage/once（执行一次后移除）/async（后台不阻塞）/asyncRewake(后台且 exit 2 时唤醒模型)（src/schemas/hooks.ts:31-64）。
  • prompt：交给 LLM 评估的 prompt，支持 $ARGUMENTS 占位符与指定 model（schemas/hooks.ts:62-91）——相当于内置「LLM-as-judge」钩子。
  • http：POST JSON 到 URL，headers 支持显式白名单的环境变量插值（allowedEnvVars）（schemas/hooks.ts:93-121），SSRF 防护见 src/utils/hooks/ssrfGuard.ts。
  • agent：由子代理执行的 hook（执行器 src/utils/hooks/execAgentHook.ts；另见 execPromptHook.ts/execHttpHook.ts）。

所有形态共享 if 字段：用权限规则语法（如 "Bash(git *)"）预过滤，避免为不匹配的工具调用白白 spawn 进程（schemas/hooks.ts:17-24）。

2.4 与 MCP 的关系（问题 4）：两套机制，插件可作为 MCP 的「打包外壳」

  • 独立配置面：MCP server 可不经插件直接配置——项目根 .mcp.json（需用户逐个批准/拒绝，src/utils/settings/types.ts:406 approvedMcpServers 字段；main.tsx:3953 提供 mcp reset-project-choices 重置审批），或 claude mcp add CLI（main.tsx:3924-3930）。
  • 插件内嵌 MCP：插件清单含 PluginManifestMcpServerSchema（schemas.ts:893），插件可直接自带 MCP server；甚至支持 MCPB/DXT 桌面扩展包格式——下载、解压、把 DXT manifest 转成 MCP 配置，并支持「需用户配置」状态机与 per-plugin 存储变量替换（src/utils/plugins/mcpPluginIntegration.ts:30-70、pluginOptionsStorage.ts）。
  • 共存命名空间：main.tsx:2791 注释明确区分 plugin:* 键与手工 .mcp.json 条目——两来源在同一 server 注册表中以命名空间并存。

定位结论：MCP 是「工具供给协议」，Plugins 是「分发与生命周期框架」；插件把 commands/agents/skills/hooks/MCP servers 打成一个可版本化、可市场分发的单元。二者正交且可嵌套。

2.5 沙箱与权限模型（问题 5）：声明式组件零代码执行，hook 全权运行，靠准入治理兜底

成分运行方式隔离手段
插件本体（commands/agents/skills/output styles）Markdown/JSON 声明文件，由主进程解析吸收，不含可执行代码天然无需沙箱；风险在提示内容而非代码
Hooks（command 型）spawn shell 进程，以用户完整权限运行无内置隔离（推测：官方立场是 settings 属于用户本机信任域）；治理靠企业管理 managedPlugins.ts/pluginPolicy.ts/pluginBlocklist.ts 准入控制
Hooks（http 型）主进程外发 HTTP POSTSSRF 防护（src/utils/hooks/ssrfGuard.ts）+ header 环境变量插值须显式 allowedEnvVars 白名单（schemas/hooks.ts:106-119）
Bash 工具沙箱设置OS 级沙箱（network/filesystem/excludedCommands 等键，settings.ts:579-591）注意：这是约束模型的 Bash 工具的，并非约束 hooks 本身
PreToolUse hook 决策权可返回 allow/deny/ask 直接参与权限判定（utils/hooks.ts:345）hook 即权威，因此 hook 配置本身的写入权就是最高权限

小结：Claude Code 的安全模型是「配置即信任」——能写你 settings.json/hooks 的东西就能全权执行命令；它选择的防线是分发侧治理（官方市场校验、仿冒名拦截、blocklist、企业策略）而非运行时沙箱。

2.6 与 CrewRouter 插件系统的对比借鉴（问题 6）

CrewRouter 现状参照：server/plugins/host.js:8-17（vm 沙箱 + permissions 数组：storage/network/gateway:modify/pages:register/routes:register/provider:register/apikey:modify/billing:modify/cron:register）、server/plugins/host.js:24-29 网关钩子五件套（gateway:requestReceived/beforeUpstream/upstreamResponse/responseChunk/finalResponse）、server/plugins/hooks.js:9 钩子管线（payload 原地改/返回替换、priority 排序、熔断摘除、零订阅者旁路）。

值得借鉴的设计

  1. 权威阻断 + 理由回灌闭环：Claude Code 的 PreToolUse deny 不是「记录一下」，而是替权限系统做决定，且阻断原因会作为 feedback 回到模型上下文让它自我修正；PostToolUse 更有 preventContinuation 硬终止（toolHooks.ts:113-130）。对照我们的 gateway:requestReceived 目前只能改 payload：建议引入显式 {action:'block', reason} 决策，reason 可选择回注为对客户端可见的错误体或对上游的替代请求。
  2. Hook 多形态（尤其 prompt/http 型）：LLM-as-judge 的 prompt hook（schemas/hooks.ts:62-91）意味着「策略检查」不必写代码，一段 prompt 就是一个合规审查器；http hook 则让外部审计服务零侵入接入。我们可在网关钩子旁增加 {type:'prompt'}/{type:'http'} 的轻量 hook 声明通道（跑在 host 侧、受同一权限门控）。
  3. 预过滤 if 条件：用规则语法（"Bash(git *)"）在 spawn 前过滤（schemas/hooks.ts:17-24），与我们 hasSubscribers() 零开销旁路同思路但更细——可下放到 payload 维度（如仅当 provider/model 匹配才进入管线）。
  4. once/async/asyncRewake：后台化 hook + 完成后唤醒（utils/hooks.ts:202-212）对网关场景的映射是「响应结束后异步任务再主动推送/记账」，适合计费调整、事后审计类插件。
  5. additionalContext/systemMessage 注入：hook 可向模型上下文注入文本——对应到我们，可让 beforeUpstream 支持声明式追加 system prompt 片段，而不仅是改写现有字段。
  6. manifest 即文档的能力面声明：一张清单列全 commands/agents/skills/hooks/mcpServers/lspServers/settings/userConfig（schemas.ts:884-898），安装前即可静态审查插件能干什么。我们的 plugin.json 已有 permissions 数组，方向一致；可补「声明式组件段」（如页面插槽之外的 cron 已有），并让商店展示能力摘要。

我们已有、Claude Code 反而没有的

运行时硬隔离：vm 沙箱 + 每钩子 2s 超时 + ctx.fetch 10s 超时 + SSRF 校验 + 连续错误熔断自动摘除（host.js:41-46、hooks.js:11-14）——Claude Code 的 shell hook 完全没有这些。我们的弱点是插件必须写成 JS 模块、门槛高于「一行命令一个 hook」；上述第 2 点的多形态声明正好补这个短板。

3. Codex CLI（新一代插件市场 + 直接兼容 Claude 语义的 Hooks 引擎）

源码：codex/codex-rs（Rust workspace，约 90 个 crate）· 置信度：高

3.1 插件形态（问题 1）：Marketplace 分发的声明式资源包

  • 新旧两代并存：遗留机制是 notify——config 里指定一个外部程序 argv，在特定节点被调用（hooks/src/registry.rs:40-42 legacy_notify_argv）；新机制是完整的 Plugin + Marketplace 体系。
  • 插件清单：PluginManifest 含 name/version/description/keywords 与 paths 资源段——可声明 skills、mcp_servers、apps、hooks 四类组件（plugin/src/manifest.rs:9-27）；hooks 可内联定义也可引用外部文件（manifest.rs:33-37 PluginManifestHooks::Paths|Inline）。
  • Marketplace 分发：插件来源三种——Local 路径 / Git(url+path+ref+sha) / npm(package+version+registry)（core-plugins/src/marketplace.rs:127-141）。运营策略字段丰富：安装策略 NOT_AVAILABLE/AVAILABLE/INSTALLED_BY_DEFAULT（marketplace.rs:165-177）、鉴权策略 ON_INSTALL/ON_USE（:178-186）。安装动作在 marketplace_add/install.rs 物化到本地。

3.3 Hook 系统（问题 3）：引擎名就叫 ClaudeHooksEngine——公开承认对标 Claude Code

Hook 点位（9 个事件）

3.4 与 MCP 的关系（问题 4）：MCP 三重身份——能力源、hook 执行器、可打包资产

  • 独立配置面：MCP server 可独立于插件配置（core/src/connectors.rs 连接器体系）。
  • 插件内嵌：manifest 的 mcp_servers 段让插件自带 MCP 能力（plugin/src/manifest.rs:29-35）；apps 类资源配合 MCP 路由（app_mcp_routing.rs）。
  • hook 执行载体：HookHandlerType::McpTool（protocol.rs:1528）+ 专门的 hooks/src/engine/mcp_runner.rs（含 HookMcpExecutor，engine/mod.rs:25）——hook 处理逻辑可以部署成 MCP tool，由远端服务承担。

定位结论：Codex 把 MCP 从「工具供给」进一步升格为「hook 计算载体」，插件则是把这些资产打包分发的容器。三者正交、互相嵌套。

3.5 沙箱与权限模型（问题 5）：无代码沙箱，但有显式 Hook 信任状态机 + 环境变量清洗

机制说明证据
Hook 信任状态机每个 hook handler 带 HookTrustStatus；配置层提供 bypass_hook_trust 开关；TOML 与 JSON 来源的 hook 收敛到同一信任身份，避免「换个文件就绕过审批」engine/mod.rs:33、registry.rs:43、discovery.rs:744
环境变量清洗hook 子进程启动前 scrub_non_inheritable_env_vars 剔除不可继承的敏感变量registry.rs:33
工具沙箱体系Rust workspace 有完整 OS 级沙箱 crate 族：linux-sandbox/、windows-sandbox-rs/、bwrap/(bubblewrap)、execpolicy/、network-proxy/、process-hardening/注意：这些约束的是模型工具执行，不是插件/hook 本身
插件本体声明式资源（Markdown/清单），无进程内可执行代码，装载零代码执行风险plugin/src/manifest.rs 全文无代码加载路径

与 Claude Code 相比：同样不搞插件运行时沙箱，但 Codex 多了显式信任审批流（trust status per hook）和子进程环境清洗两个防御纵深；OS 沙箱工程化程度也更高（专用 network proxy + exec policy）。

3.6 与 CrewRouter 插件系统的对比借鉴（问题 6）

值得借鉴的设计

  1. updated_input 结构化改写通道：Codex 把「hook 改写入参」做成显式字段而非整体 payload 替换。我们的 gateway:beforeUpstream/gateway:requestReceived 目前靠「返回非 undefined 对象即视为替换整个 payload」（server/plugins/hooks.js:9 约定）——建议约定合并语义（浅合并或字段级 diff），降低插件误覆盖整包的风险。
  2. Hook 信任状态机：per-hook trust 审批 + 跨配置源收敛信任身份（discovery.rs:744）。我们的 vm 沙箱在运行时已隔离，但「新装插件的钩子在首次生效前需人工确认」这层产品流程仍可借鉴，尤其针对从商店批量安装的场景。
  3. MCP 作为 hook 执行器：McpTool 形态意味着重策略（内容审核、合规检查）可以外置为服务。我们网关侧可考虑允许 hook handler 声明为 {type:'mcp', server, tool}，host 代为调用——天然获得异步化与横向扩容。
  4. 市场运营元数据：安装策略三态 + 鉴权时机两态（marketplace.rs:157-182）+ interface 展示段（capabilities/default_prompt/logo）。我们的插件商店统计上报可吸收这套字段。
  5. 行业信号：引擎直接命名 ClaudeHooksEngine 说明 Claude Code 的 hook wire format 已是事实标准。CrewRouter 若做「多 harness 兼容钩子层」，对齐 CC/Codex 的事件名 + 输入输出 JSON 结构是最省力的互操作路径——我们的网关本来就转发这两家流量。

我们已有、Codex 没有的

vm 沙箱 + 权限数组 + 钩子超时熔断（见 2.6）依旧领先；Codex 的 command hook 同样是无沙箱全权 shell。
