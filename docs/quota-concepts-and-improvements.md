# 用户组、额度与限额：现状核对及低风险改进方向

## 1. 评估范围与结论

本报告核对 `/data/CrewRouter` 自有 `server/`、`public/` 的现行源码、DDL 与页面挂载，不依据字段名推断行为。未读取真实 `config.json`、环境凭据、数据库、日志或用户数据；未启动服务、执行初始化、迁移或数据库审计。UI 核验指实际 HTML、渲染脚本与请求接口的静态追踪，不是登录真实实例的浏览器验收。

核对日期：2026-11-11。开始时工作树干净；评估过程中其他工作更新了 API 鉴权、积分准入、余额及相关测试。本文按最后复核时的工作树描述，基准 HEAD 为 `7f69e4f8`，并包含当时尚未提交的修复；引用行号随后续修复可能移动。本任务只新增本文，不修改、暂存或提交这些源码。

**核心结论：**

1. “用户组”已不是主请求的计费政策来源。实际来源是 `users.team_id → teams.quota_rules`，但旧表、旧字段、响应字段 `group`、演示数据仍保留旧概念。
2. Team 同时承担模型授权、注册分配、个人容器和额度模板，**额度是按用户统计，不是 Team 成员共享池**。
3. 当前正常管理写入倾向于“一个用户唯一 Team”，但数据库及模型授权仍支持多 Team。历史/特殊路径产生多 Team 时，模型权限取成员关系并集，普通请求额度只读 `users.team_id`；不会合并所有 Team 的规则，也不随模型库当前 Team 切换。
4. 所谓“限额规则”更接近“免积分额度”：任一规则有余量即可免费，全部耗尽后转扣积分；不是任一上限命中即拒绝，也不是永久免费。
5. RPM/TPM、普通积分、可退款资金及供应商账户额度不是同一种额度。当前页面缺少主体、单位、窗口和超额行为的说明，且存在真实计量/入口一致性问题，不能只换名字解决。

## 3. 同一用户多 Team：哪些规则实际生效

### 3.1 正常管理写入与遗留多成员读取不是同一模型

- 管理员编辑用户明确拒绝旧 `group_id`，使用 `team_id`（`server/routes/admin.js:181,286`）。
- Team“添加成员”调用 `setUserTeam`（`server/routes/teams.js:214–228`）。该函数先删除用户的**全部** `user_teams`，再写目标 Team，同时更新 `users.team_id`（`server/utils/team-membership.js:5–16`）。因此“加入 B”实际上是从 A **转组**，不是增添一个组织身份。
- 移除目标成员时也是调用 `setUserTeam(..., null)`，会清空所有成员关系与投影（`server/routes/teams.js:266–271`）；对于历史多成员用户，不是只退出当前 Team。
- 成员列表按 `users.team_id` 查（`server/routes/teams.js:177–185`），Team 列表成员数按 `user_teams` 汇总（同文件 `23–29`）。不一致数据会出现“人数不等于成员列表”的真实显示问题。
- 模型库仍枚举全部 `user_teams`，按 Team 分组（`server/routes/user.js:2339–2395`）；普通请求授权经 `getAuthorizedModelInputs`，按全部成员关系找启用模型（`server/routes/api.js:434–437,479–483`；`server/utils/resolved-model-access.js:17–32`）。

### 3.2 条件案例：用户主 Team=A，另有成员关系 B

| 操作/入口 | 生效来源与结果 |
|---|---|
| 在模型库查看 A、B | 均可显示，模型权限取两者可用模型并集 |
| 普通 API 调用只有 B 授权的模型 | 只要 Key 绑定/请求路由也允许该模型即可通过模型权限；**额度仍用 A** |
| 普通 API 免费额度/实扣 | 仅 `users.team_id=A` 的规则；历史用量按用户全量统计，不区分模型来自 A 还是 B |
| 页面“Team 与限额”、`POST /api/user/usage` | 均读 A 的规则，以 `group` 字段返回；不展示 B 的另一套额度 |
| `users.team_id=NULL` 但还有 B 成员关系 | 模型权限可来自 B，普通 API 没有 Team 免费额度，需普通积分 |
| 通过管理端“添加到 B” | 删除此前全部成员关系，主 Team 与成员表同步为 B；旧用量不清零，立即按 B 的模板套用用户历史 |
| 模型归因检测 | **例外**：根据可访问模型 JOIN 得到 `ut.team_id`，取查询首行；没有稳定的 Team 优先级，然后保存为任务 `team_id` 并用于预算覆盖检查 |

模型归因例外证据：`server/utils/model-trace-store.js:41–60,75–104,133–153`。同一模型同时授权于两个 Team 时，查询只 `ORDER BY m.name`，不能稳定选择主 Team；不同于普通网关。这是条件可达的确定性缺口，不代表线上已有此数据。

**答案不是“多 Team 额度叠加”，也不是“取最严格规则”。** 当前是“授权多成员并集 + 普通计费单投影 + 个别专用入口另选 Team”的混合状态。

### 3.3 默认 Team 与个人 Team

- PassPort 注册：邀请 `team_id` 优先，其次默认 Team，否则创建个人 Team，写两份归属（`server/routes/passport-auth.js:94–114`）。飞书初始分配也是有默认则加入、否则个人，且不会覆盖并发管理员分配（`server/utils/team-membership.js:19–42`；`server/routes/feishu.js:362`）。
- 默认 Team 是新用户分配规则，不是全局兜底额度层，不会叠加到所有已有成员；改默认不会在此路径批量移动老用户。
- 启动为未分配用户补个人 Team（`server/index.js:1544–1572`），不是为所有用户额外保留个人额度。
- 桌面本地路径有独立个人容器保证函数，发现没有个人 Team 会插入成员关系（`server/utils/local-passport.js:163–179`）；不能用普通管理端唯一归属逻辑推断所有环境都绝无多成员。
- 个人 Team 禁止删除、添加或移除成员（`server/routes/teams.js:142–145,211–212,258–259`），但“个人”标志不等于固定免费套餐，额度仍来自其 JSONB 规则。

## 4. 额度、窗口、速率和余额的真实调用

### 4.1 quota rules 是额度覆盖策略，不是硬拒绝阈值

`server/utils/points-deduct.js:14–73,76–99`：

- `requests` = 窗口内 `usage_records COUNT(*)`；`tokens` = `SUM(weighted_tokens)`。
- 窗口起点是 `Date.now() - duration_hours`，属于滚动回看；24 小时不是本地自然日，720 小时不是自然月。页面把 720 小时格式化为“1 月”（`public/js/app.js:6769–6777`；管理端 `public/js/admin.js:10904–10912`）容易产生错误的重置预期。
- 检查还加上未落聚合表的内存缓冲，以及已被免费额度覆盖的归因检测预留。
- 任一规则 `used < limit` 即免费；全部规则耗尽后按加权 Token 扣积分。没有规则是付费，不是无限免费。
- 普通 API 最新准入统一调用 `canConsumePoints`：有任一可用额度，或普通积分大于零即可；缓存命中每次重读 `team_id,balance`（`server/routes/api.js:1235–1242,1290–1293`）。**旧版准入用任一超额、结算用全部超额的矛盾已在本次看到的修复中消除，不再作为现存 bug。**
- Playground 的修复后准入也读取 `balance, team_id` 并调用 `canConsumePoints`（`server/routes/playground.js:79–83`），不再单凭两种余额之和判断；它的记账逻辑仍是独立入口（同文件 `611–723`），不能据此认为所有结算与 Agent 也已统一。
- 这是 OR 覆盖语义。例：请求额度耗尽而 Token 额度尚有余量，仍免费；不能宣传为“每日请求硬上限”。是否改 AND 或拒绝，必须由产品决策，不能以清理术语之名改变付费结果。

### 4.2 原始 Token、加权 Token、积分

计算实现为 `server/utils/billing.js:79–129`：

- 缓存读取部分从输入中拆出，按 0.1 倍；图片输入可应用 `image_ratio`；输出及其他输入再统一乘模型倍率，最后四舍五入为加权 Token。
- 标准理论积分为加权 Token / 1,000,000；实扣还受免费额度及计费插件影响。API 计费插件入口在 `server/routes/api.js:990–1003`；所有额度耗尽的分支在 `points-deduct.js:99` 直接按加权 Token 计，不使用传入的插件后费用，应明确这一优先级。
- `tokens_used` 是明细的原始统计值，`weighted_tokens` 是计费计量，`cost` 在主事务中写实扣。用户 `/usage` 的 `total_tokens` 求原始量，规则的 `tokens` 求加权量（`server/routes/user.js:1935–1940,1958–1975`）；同屏两个 Token 数不同不一定是错误，缺单位才是核心问题。
- 请求次数是账单记录数。Fusion 汇总可写一条，Agent 可写单独调用记录，失败/重试有另一个请求观测链；不应承诺“一个客户端请求永远等于一次额度请求”。普通 Fusion 写入可见 `server/routes/api.js:3570–3594`。

### 4.3 RPM/TPM 是另一层、另一种窗口

`server/routes/api.js:1006–1025,3192–3216` 表明：

- 用户配置与模型配置两个正值取较小者；零表示这一层不限制。
- 普通 Chat 桶键为 `rpm:userId:model`、`tpm:userId:model`；不同 Key 共享同用户同模型桶，不同模型不共享一个用户总桶；模型限制也不是跨全部用户的供应商全局总桶。
- 窗口从建桶开始，超过 60 秒重建，不是 Team 的小时滚动窗口；状态是本进程 Map，重启/多实例不能保证全局硬限流。
- TPM 用输入消息长度 / 4 的估算（空值兜底 500），未在该检查中按最终输出和加权量结算。拒绝检查前已递增计数。它更接近“每分钟估算输入 Token 限速”，不是账单 Token 上限。

因此“用户 RPM=60”当前不应解释为“此用户全模型合计每分钟绝不能超过 60 次”。这是实现作用域事实；是否改全局桶、分布式计数、预估加实耗对账，需要另立需求。

### 4.4 积分、退款资金与预扣不能混为一账

- 主倍率模式 `deductPoints` 只锁/扣 `users.balance`；修复后的准入也只看普通积分或免费额度（`server/utils/balance.js:523–564`；`server/utils/points-deduct.js:80–99`）。
- 旧 `deductBalance/executeDeduct` 支持普通余额优先，再从可退款明细按手续费率降序扣除（`server/utils/balance.js:100–185`）。`preConsumeBalance/settleBalance` 使用 `balance_preconsumes` 并支持差额结算（同文件 `38–51,300–466`）。本次自有生产 JS 检索未发现这些旧预扣函数被主 API/Playground 调用，不能写成“每次网关请求都预扣”。
- 模型归因检测是真实在用的专用预算预留：`checkFunds` 检查覆盖，后续以 `reserved` probe 占用额度/预算（`server/utils/model-trace-store.js:75–104,145–170`）。该预留和旧余额预扣表不是一套机制。
- 管理退款接口处理的是扣手续费后的净退金额，维护明细面额和汇总，并不等于模型积分扣费（`server/routes/admin.js:327–421`）。用户余额接口返回的 `refund_balance` 实际是净可退值，而管理列表/用户表同名字段是面额汇总（`server/routes/user.js:1840–1844,1890–1895`；`server/routes/admin.js:113`）。
- 仍有入口不一致：Agent 的 `assertHasBalance` 相加两种余额且不看 Team 免费额度，生成/线程入口调用它，但实际记账用只扣普通积分的 `deductPoints`（`server/utils/agent-billing.js:33–47,66–72`；`server/routes/agent.js:280,447`）。因此普通积分为零但额度可用会被先拒绝；只有退款资金则可能先通过、结算失败。应作为入口 bug 单独修复，而非把退款资金悄悄并入积分。

### 4.5 平台 Key 与供应商 Key

平台 API Key 的 DDL 包含归属用户、禁用/过期、计划字段、模型绑定、权限和预警开关，未定义独立金额/Token 预算字段（`server/scripts/init-db.js:475–505`）。实际请求实时检查禁用/过期并重新授权模型队列、Harness/Fusion 绑定（`server/routes/api.js:440–495`）。不应把“额度预警”或某个 Key 页面中的模型配置称为“Key 独立额度”。计划字段是否每条协议路径都执行不在此报告做完整安全保证。

供应商 Key 是平台访问上游的凭据，可按 Key 查询上游账户并聚合部分余额结果（`server/utils/provider-quota.js:485–529`）。用户供应商额度接口按 Team 的模型关联和 `hide_provider_quota` 控制可见性，读取缓存快照并带更新时间、失败/陈旧状态（`server/routes/user.js:3490–3557`）。多成员情况下，只要存在未隐藏的关联路径就可见，不是隐藏 Team 全局否决。

普通 API 的个人准入路径没有把 `quota_last_result.remaining` 纳入个人额度计算；真实上游不足仍可能返回上游错误。关闭“额度查询”不等于停用上游或关闭平台积分限制。

| Team“添加成员”与 `setUserTeam`（`server/routes/teams.js:194–228`） | 保留原 Team，额外加入 | 实际转组并撤销此前全部成员关系，影响权限和计费政策 |
| 余额响应把当前 Team 命名为 `group`（`server/routes/user.js:1883–1895`） | 这是旧用户组的规则 | 实际来自 `teams`；字段兼容不应再透传为产品术语 |
| 演示数据仍同时给 Team 和“标准组/高级组”（`server/demo/data.js:22,38–43,448–449,496–498,601–606`） | 两层都在真实系统生效 | 演示与生产路径不一致，不能拿演示页面证明现行业务 |
| 供应商额度与个人限额都称“额度”（`public/pages/admin.html:940,1981`；`public/js/admin-model-library.js:167–175`） | 供应商剩余额度是分给自己的余额 | 账户共享参照；前端已有“账户额度参照/按成员估算”，但仍需所有卡片明确主体与估算属性 |
| 模型倍率说明（`public/pages/admin.html:1730–1732`） | 输入加上缓存再计一次 | 概述公式未强调输入需剔除缓存；应与 `billing.js:89–110` 的拆分口径统一 |

## 6. 真实问题、产品选择与待验证风险

### 6.1 可从当前调用链确定的问题

1. **重复计量及显示/判定分叉。** 普通 Chat 在成功写 `usage_records` 后又 `recordQuotaData`（`server/routes/api.js:3378–3388`），`checkQuotaRules` 同时求明细再加同一请求的缓冲（`server/utils/points-deduct.js:33–60`）。缓冲并不是“尚未写入明细”的请求，而是尚未写入另一张聚合表的请求。分钟刷新清空后同一历史请求不再多算；小时边界截断还使窗口边缘的重复量不稳定（`server/utils/quota-data.js:21–24,54–73`）。后果是提前判超额，过一会又恢复。余额页只读明细而不读缓冲/归因预留（`server/routes/user.js:1859–1880`），于是与准入、签名数值分叉；签名也再加缓冲且不含检测预留（`server/utils/api-signature.js:145–158`）。应先定义唯一明细账，再去重聚合缓冲，不以改标签掩盖。
2. **边界请求因记账顺序而待遇不同。** 普通事务先插入当前明细再锁用户重算是否免费（`server/utils/balance.js:592–603`），Agent 先判断/扣款再插入（`server/utils/agent-billing.js:33–46`）。设唯一请求额度=1、此前用量=0：普通准入允许，但结算含本次后已达 1，可能收费或因零余额失败；Agent 结算看到此前为 0，覆盖本次。应统一“额度覆盖本次还是覆盖此前请求”及边界跨额处理，然后按同一事务协议实现。
3. **空 Team 删除引用没有现行建表的映射表。** `server/routes/teams.js:160` 先删除 `user_group_team_map`；本次 `server/` 检索只在此运行查询及测试 fixture 建表中找到它，没有生产建表/迁移。全新库若确无该表，删除空 Team 会因缺表回滚。静态条件缺陷成立；未查真实数据库，不能声称现网已报错。
4. **多成员的投影/列表/计费来源不一致。** 详见第 3 节；数据库允许但正常管理写入清空其他成员，且归因检测会选不稳定的授权 Team。这不是单纯语言问题。
5. **Agent 准入与结算资金口径不一致。** 详见 4.4；与本轮已统一的普通 API 准入不要混为同一状态。
6. **默认 Team 唯一性有并发缺口。** 管理更新先清空默认再单独更新目标，不在同一事务；DDL 只有布尔字段，无默认为真的部分唯一索引（`server/routes/teams.js:74–89`；`server/scripts/init-db.js:396–409`）。并发设置不同 Team 可能同时成为默认，注册多数路径 `LIMIT 1` 又无排序。属于静态可达竞态，实际数据未核实。

### 6.2 不能未经决策就“修正”的产品选择

- 规则 OR 还是 AND；超额拒绝、付费继续或通知确认。
- Team 是权限组织还是套餐模板；是否允许多 Team；团队是否共享资金/额度。
- 小时滚动窗口还是自然日/月；采用哪个时区；无规则究竟付费还是免费。
- 用户速率按每模型还是全模型；模型速率按每用户还是全局共享；单机软保护还是分布式硬限制。
- 可退款资金是否可消费，兑换率、扣减顺序、手续费和退款责任；主网关目前“不消费退款余额”不应直接被标为财务 bug。
- 计费插件与免费额度/超额积分的优先级；计费切换或转组是否追溯窗口内历史。

### 6.3 风险但本报告未做动态证明

额度查询失败返回无规则（`server/utils/points-deduct.js:18–24`），可能把原本免费用户转成按积分付费，需确定失败策略；普通准入只验证余额大于零，未预留足够支付整次输出的成本，可能上游已完成而实扣失败。还需在隔离环境验证并发重复提交、流式中断、跨实例计数、窗口边界、切组与在途请求交错。本文没有把这些写成线上事故。

## 7. 建议的统一术语与信息架构

| 当前名称 | 建议用户名称 | 必须随附的信息 |
|---|---|---|
| 用户组 / Team 混称 | 团队（Team）；“旧用户组”仅限迁移页 | 团队身份与“当前计费政策来源”分开标注 |
| Team 限额规则 | 成员免积分额度（当前语义） | 每成员独立、滚动最近 N 小时、任一规则可覆盖、全部耗尽后付费 |
| `requests` | 计费请求记录数 | 明确非消息条数，Fusion/Agent 如何计数 |
| `tokens_used` | 原始 Token | 输入/输出/缓存构成、真实/估算质量 |
| quota rule `tokens` | 加权 Token 额度 | 倍率、缓存折扣、图片权重；不要改数据库枚举即悄悄改计量 |
| `balance` | 可用积分 | 至少展示小数或自适应精度；列出理论费与实扣费 |
| `refund_balance` | 可退款面额 / 预计净可退金额 | 两值分别命名；手续费率和是否可用于调用 |
| rate limits | 请求速率限制 / 估算 Token 速率限制 | 主体、按模型还是全局、60 秒窗口、部署范围 |
| provider quota | 上游账户额度（共享参照） | 供应商/账户标识、单位、周期、最新有效采样时间、陈旧/估算状态 |
| API Key 额度 | API Key 权限与模型绑定 | 没有独立预算就明确“与同用户其他 Key 共用个人额度/积分” |

建议保留管理模型库为授权入口，但在 Team 详情明显分出“成员与权限”“成员免积分额度”“上游额度可见性”三个区块。用户积分页展示一张“当前生效政策”摘要：计费 Team、计量单位、窗口、组合方式、超额行为、普通积分、各 Key 是否共享。供应商卡片不要再给出类似个人剩余权益的合计，异构单位不能直接求和。

API 可先增加 `billing_team` / `effective_policy` 等明确字段，并保留 `group` 兼容别名一个弃用周期；不要直接删除旧字段导致 cc-switch、插件或 SDK 断裂。

## 8. 逐步低风险演进

### 第 0 步：先冻结语义与建立可重复样例

- 由产品确认第 9 节选项，记录当前规则版本，不修改历史费用。
- 在隔离数据库构造：无规则、单请求、单加权 Token、双窗口 OR、只有退款资金、两 Team 不一致、同模型双 Team、切组、归因预留、分钟 flush 前后与多实例样例。
- 只计划在获得授权后运行一致性审计；现有 `server/scripts/audit-team-consistency.js:6–34` 检查投影和孤儿，但不专门报告成员数大于一，也不报告多默认；需要补齐只读诊断后再谈迁移。不要把脚本选择的“最早成员”自动当成产品确定的计费 Team。

### 第 1 步：先修账本与入口一致性，不改商业政策

- 保持当前 OR + 超额付费策略，建立可复用政策读取/计量服务，页面、准入、结算、签名、Agent、归因任务复用相同口径。
- 消除 `usage_records + 同源聚合缓冲` 重复计数，保留有独立身份的真实预留；聚合只用于报表，计费只能消费一份权威账本/幂等预留。
- 统一边界事务：锁定用户与政策版本 → 识别本次请求 → 判断覆盖 → 写账/扣费，避免有的入口先写用量、有的后写；增加幂等请求标识与失败回滚验证。
- Agent 准入与倍率网关一致；修空 Team 删除的缺表依赖；并发默认选择改事务与数据库约束，但约束前先诊断，不能自动删除冲突数据。
- 验收：额度=1 的首个请求免费、第二个按约定收费；flush 前后同一用户用量不跳；余额页与准入在同一快照解释一致；失败不能漏账、双扣或悄悄转付费。

### 第 2 步：只改可见文案和兼容响应

- 上线第 7 节术语；“添加成员”若仍为唯一归属就改“转入此团队”，显示将移出的团队与权限变化，要求确认。
- 将“1 月”改“滚动最近 720 小时（30 天）”；“暂无限额”改“未配置免积分额度，调用按积分计费”。
- 积分提高显示精度；Team 规则显示“成员独立额度，非团队共享”；供应商额度明确上游账户与更新时间。
- 演示数据与生产 API 契约同步；旧 `adminUserGroups` 只做明确重定向，权限描述也不再宣称有独立用户组管理。

### 第 3 步：归属模型收敛，分两条互斥路线

**推荐低风险路线 A：当前产品继续唯一计费/权限 Team。** 先人工确认冲突用户归属，输出迁移预览；在写入口全部统一后，考虑为 `user_teams.user_id` 加唯一约束，逐步选定一个权威来源，旧投影仅兼容读取。桌面个人容器另行定义，不能硬删。历史用量不回填成推测出来的 Team 账单。

**路线 B：确实需要多团队。** 保留成员关系并集，但显式引入“主计费政策”或请求/Key 的计费上下文；模型授权 Team 与支付 Team 分离。明确共享池、优先级、叠加或最严规则，再增加请求/账单政策快照。禁止继续用任意 JOIN 首行选 Team。先影子评估新旧结果，用户确认后按版本切换，不能把所有 Team 额度简单相加。

两路线都应让普通 API、模型归因和 Agent 对相同计费上下文得出一致结果；在产品未决定前，**不增加用户多 Team 切换控件来伪装已有确定计费能力**。

### 第 4 步：商业政策和速率能力显式版本化

需要硬上限、自然月、共享资金池或分布式速率时，新建明确的策略版本/字段，例如主体、指标、单位、窗口、组合方式、超额动作；先新用户/测试 Team 灰度，再迁移存量。对比旧/新预期费用与拒绝结果，保留回滚到旧版本能力。财务退款账本独立审计，绝不靠给同一 `balance` 字段换单位完成迁移。

## 9. 需用户/产品明确决策

1. **组织模型：** 一个用户只能属于一个 Team，还是多 Team 是正式需求？桌面个人容器是否独立于组织成员关系？
2. **付费归属：** 多 Team 时用主 Team、Key 指定、请求选择还是其他规则？是否允许使用 B 的模型却消耗 A 的权益？
3. **规则语义：** 维持任一有余量免费，还是所有上限都满足？全部用完后自动付费、硬拒绝还是先通知确认？
4. **额度主体：** 成员独立模板还是团队共享池？转组后继续携带个人窗口历史还是按新的政策账本计数？
5. **边界：** 本次请求恰好耗尽/跨过 Token 额度时，整次免费、整次收费还是仅收超出部分？API 与 Agent 必须同答。
6. **时间：** 保持滚动小时还是自然日/月？采用哪个时区，是否有明确重置时间？
7. **财务：** 普通积分与退款资金是否互通？若互通，兑换比例、手续费、消费顺序、退款责任如何定义？
8. **速率：** 用户/模型限制是否要求全局聚合及跨实例硬保证？TPM 包括输出、图片与缓存吗，按原始还是加权？
9. **故障策略：** 额度读取失败、预留超时、上游成功而结算失败时，拒绝、延后对账还是允许受控欠费？能否接受静默转成付费？
10. **旧结构退出：** 是否确认停用旧用户组，对外 `group` 字段与旧权限名称的兼容期多长？未查真实数据前不删除 `group_id`、旧规则表或历史映射。
