1. 总体概览：流式与缓存横向速览

流式响应是所有 harness 与模型之间的唯一传输形态——八家无一例外使用 SSE（或其变体）接收增量输出；prompt caching 则是成本结构里杠杆最大的单一变量：同一次会话的重复前缀，命中与不命中的价格差在 Anthropic 上是 10 倍（读 0.1×、写 1.25×）。本报告把两个主题合并研究，因为它们在源码里共享同一个模块：请求拼装与流解析。

partial JSON 容错

content_block_start 时把 tool_use 的 input 初始化为空字符串，此后每条 input_json_delta 只做纯字符串拼接 contentBlock.input += delta.partial_json（claude.ts:2113），绝不边流边 parse；解析推迟到 content_block_stop 由 normalizeContentFromAPI 统一执行（claude.ts:2196-2199）。防御面：delta 引用不存在的 block index 直接抛 RangeError('Content block not found')（claude.ts:2056-2064），类型不符抛错并上报 tengu_streaming_error 遥测（claude.ts:2060-2111）。乱序容错的答案是 index 寻址——内容永远追加到 contentBlocks[part.index]。

超时与重试：分层看门狗 + 整请求重放

  • 三层超时：30s stall 检测（只在下一事件到达后事后判定，claude.ts:1936,1947-1966）；90s 流级 idle watchdog（默认关闭，需 CLAUDE_ENABLE_STREAM_WATCHDOG，超时 abort 并抛 'Stream idle timeout'，claude.ts:1869-1927）；600s 请求级超时只覆盖初始响应头不管流体（src/services/api/client.ts:144，注释自己承认了这个盲区）。
  • 重试 = 整请求重放，无 Last-Event-ID 续传：withRetry 循环重新执行整个 operation，默认 10 次、500ms×2ⁿ cap 32s + ≤25% 抖动、服务端 retry-after 优先（src/services/api/withRetry.ts:51-53,186-190,531-547）。529 连续 3 次触发 fallback model 切换（withRetry.ts:54,330-350）；unattended 模式退避 cap 放宽到 5min、总等待 6h、每 30s 心跳输出 api_retry 进度（withRetry.ts:92-99,485-505）。
  • 降级路径：流中断可降级为非流式重试（claude.ts:2503-2530，可用 flag 关闭以防双工具执行的已知缺陷 inc-4258）；ECONNRESET/EPIPE 视为陈旧 keep-alive 连接并禁用连接池（withRetry.ts:111-118,216-230）。
  • 仓库里唯一的 Last-Event-ID/from_sequence_num 续传在 src/cli/transports/SSETransport.ts:209-260——但那是 session ingress 远端桥接通道，模型 API 无续传。
完整性哲学：没有事件序号校验。收尾检查只有一条——!partialMessage || (无新消息 && 无 stopReason) 即抛 'Stream ended without receiving any events' 触发非流式 fallback（claude.ts:2341-2364），这条同时覆盖「200 但非 SSE 体」和「message_start 后断流」两种网关故障形态。stop_reason 只可能来自 message_delta，它是唯一完成判据。

2.2 缓存：把前缀保卫做成一门工程学

Claude Code 是显式断点派的极致。断点构造函数返回 {type:'ephemeral', ttl?:'1h', scope?:'global'}（claude.ts:358-374），布局是「system 多块断点 + 消息级恰好一个断点」：

  • system 层多块：buildSystemPromptBlocks 按 attribution scope 分块打标，源码注释警告「再加一块会 400」（claude.ts:3213-3238；分块策略 src/utils/api.ts:296-360）。
  • 消息层单断点：addCacheBreakpoints 每请求只放一个标记在最后一条消息上；fork 场景 skipCacheWrite 把它移到倒数第二条避免写放大（claude.ts:3062-3105,3078-3089）。

超时、重试与完整性

  • 空闲超时 300s（model-provider-info/src/lib.rs:27），机制是 tokio::time::timeout(idle_timeout, stream.next())，超时报 "idle timeout waiting for SSE"（sse/responses.rs:553-578）；某内置 provider 收紧到 5s（model-provider/src/provider.rs:572）。无整体请求级超时。不消费 ping/SSE 注释。
  • 整请求重放：常规流错误 stream ×5 / request ×4（用户可配，硬上限 100），200ms×2ⁿ ±10% 抖动；连接故障在 feature 开启时可无限重连，5s 起指数 ×2 cap 60s（core/src/responses_retry.rs:17-124，常量 util.rs:5-8）。WebSocket→HTTPS 传输层可降级且 retries 清零重来（responses_retry.rs:85-102）。
  • 完整性：流提前 EOF → ApiError::Stream("stream closed before response.completed")（sse/responses.rs:564-569）——「必须见到 completed」是硬约束；缺 id 的流式 item 由 assign_missing_streamed_response_item_id 补齐；end_turn:false 时置 needs_follow_up 继续 turn（turn.rs:2296,2575-2578）。tool arguments 不做中途 parse，完整 String 推迟到工具执行阶段才解析（core/src/tools/router.rs:150-166），天然免疫 partial JSON 问题。

3.2 缓存：一个键值搞定，其余交给服务端

Codex 是自动前缀派的代表：请求里没有任何 cache_control，等价物是 prompt_cache_key 会话亲和键——主会话直接用 session_id，内部子代理用 {source}:{parent_thread_id} 格式继承父线程（core/src/client.rs:485-495,944-959；字段定义 codex-api/src/common.rs:270）。测试固化了它的稳定性语义：跨模型切换、跨 per-turn override 必须保持不变（core/tests/suite/prompt_caching.rs:436-439,704-707）。

4. Grok Build（三层自研采样管线 + 手工三断点）

Grok Build 的流式管线是全场架构感最强的自研实现。L1 原始解析在采样器 xai-grok-sampler/src/client.rs，同一文件支持三条后端通道：Chat Completions chat_completion_stream（:1009）、Responses API create_response_stream（:1359）、Anthropic Messages create_message_stream（:1698）；请求侧用 #[serde(flatten)] 包装注入 stream:true + stream_options.include_usage:true（:286-298），首个 chunk 手工剥离 UTF-8 BOM 以规避 eventsource-stream 0.2.3 的切片 bug（:1118-1130）。L2 是纯函数变换层，把三种后端的原始 chunk 流统一折叠为内部 SamplingEvent 枚举（StreamStarted / FirstToken / ChannelToken / ToolCallDelta / ResponseStarted / ReasoningCompleted / Completed / Retrying / Failed 等，events.rs:52-171）；后端分派在 actor 的 run_one_attempt 三分支调用（actor/request_task.rs:528-598）。

超时与重试：预算最重的实现

  • 双层空闲检测：外层 300s 默认 idle timeout 抓「完全断流」，内层内容感知计时器抓「只有 keepalive/空 delta 但无实质内容」——Messages 后端 Ping 明确不算内容（request_task.rs:34-40、chat_completions.rs:30-38,232-246、stream/messages.rs:39-50）。连接层 keepalive 常量齐全：http2_keep_alive_interval 20s / tcp_keepalive 30s / connect_timeout 30s（xai-grok-http/src/lib.rs:319-334）。

3.2 缓存：三断点设计里给网关留了第四槽位

仅 Anthropic Messages 后端发显式断点：CacheControl { type:"ephemeral" }（xai-grok-sampling-types/src/messages.rs:91-102），apply_cache_breakpoints 打恰好 3 个——system 最后一块、transcript 尾部 tip、最后一个 assistant 之前的上一条 user（sampling-types/src/conversation/messages.rs:39-73）。两处防御性细节：thinking 块跳过打点（API 拒绝）、纯文本消息升级为 block 形式承载标记（:5-37）。

HTTP 客户端超时 connect=15s, read=None(SSE 不设读超时), write=15s, pool=10s（run_agent.py:5148-5155）——读超时交给应用层的 stale detector：流式默认 180s，上下文估算 >100k 时放宽到 300s、>50k 到 240s；连续 5 次 stale 才放弃报错（chat_completion_helpers.py:812-857）；非流式 90s（2026-05 从 300s 下调加速 fallback），本地端点直接禁用。完整性上以 EmptyStreamError 作为统一的「诚实失败」信号：finish_reason 为空且无任何内容 → 拒绝伪造成功回合（:4360-4373）；部分 JSON args 按 finish_reason 分流处理——length 提取 max_tokens 重试，无 finish_reason 走 partial-stub 快速失败，避免误报「输出长度截断」（:4375-4400）。重试用 decorrelated jitter backoff 防惊群，Retry-After 支持数值与 HTTP-date 两态（agent/retry_utils.py:23-87）；并发安全靠单写者不变量 claim_stream_writer，过期流的写入直接停读（:4529-4543）。

7.2 缓存：全场最重的断点布局 + 最细的字段 fallback 表

  • 默认 4 断点：静态 system 前缀 + system 尾部 + 最后 2 条非 system 消息；无静态前缀时 fallback 为 1 system + 最后 3 条（agent/prompt_caching.py:2-7）。TTL 可配 1h。
  • Alibaba/Qwen 家族也打标：opencode/DashScope 直连等上游接受 Anthropic 式 cache_control 出现在 OpenAI wire 上（否则「零命中全价重计费」，引用 pi-mono #3392/#3393），但其上下文缓存只认 5m、拒 1h，故 TTL 钳制（agent_runtime_helpers.py:2202-2209、prompt_caching.py:124-133）。
  • 载体合法性检查：envelope 布局（OpenRouter 等）下 role:tool 空 content 的顶层标记会导致静默挂起、纯 tool_calls 空 assistant 顶层标记被忽略——两类一律跳过不打；native 布局由适配器把标记移入 tool_result block 内（prompt_caching.py:38-56,91-111）。
  • 时间戳治理：系统提示的时间行刻意 date-only——注释明言分钟精度会在压缩边界/fresh-agent/resume 等每次重建时击穿 prefix-cache KV（PR #20451）；timezone 全天恒定才附带保证 byte-stable；永生会话干脆去掉日期只留时区（agent/system_prompt.py:848-894）。
  • builder 注册式 stable-prefix：skill/webhook/cron 在构造期注册静态 scaffold，运行期取最长真前缀拆分为「stable_prefix(带断点) + 易变尾巴(不带)」，刻意不做分隔符启发式防止易变字节被吸进缓存体；注册表 LRU 32 条/4MB，命中即刷新防高频 cron 任务挤出（agent/prompt_cache_boundary.py:21-88、prompt_caching.py:62-78）。
  • usage fallback 表全场最全：normalize_response_usage 归一三种 API 形态，读侧兼容 OpenAI cached_tokens、Anthropic 顶层字段（OpenRouter/Vercel/Cline 类代理转发场景）、DeepSeek prompt_cache_hit_tokens、Kimi 顶层 cached_tokens；写侧四级 fallback；还有 per-model 缓存单价表（0.10～1.50 USD/M）与 MiniMax-M3 特例观测——其 cache_read_input_tokens 恒带 +128 底噪、creation 恒 0，不可作命中信号（agent/usage_pricing.py:123-380,1280-1417）。

8. OpenClaw（一 provider 一 transport + 声明式缓存界碑）

8.1 流式：注册制 transport，渠道永远不碰原始 SSE

OpenClaw 的架构是「一个 provider 一个 transport 文件」的注册制 monorepo：packages/ai/src/transports/anthropic-transport-stream.ts（Anthropic Messages SSE）、openai-completions-stream.ts、Responses 支持 transport: "sse"|"websocket"|"websocket-cached"|"auto" 四种传输（transports/openai-responses-websocket-client.test.ts:269）。各上游协议在 packages/ai 内被翻译成平台无关的 AssistantMessageEvent 流；Telegram/Discord 等聊天渠道从不直连模型——Gateway 把 agent 事件流投影成 snapshot/delta 给各通道渲染（src/gateway/live-chat-projector.ts:20-44）。首 SSE 事件看门狗：HTTP 头已开但 N ms 内无首个事件即 abort，Azure 固定 30s（utils/stream-first-event-timeout.ts:50-66、openai-responses-contracts.ts:24）。

partial-json 边流边解析 + 乱序容错

与「攒完再 parse」的主流做法不同，OpenClaw 用 partial-json 库边流边出中间值（未闭合 JSON 也能产出可用的部分参数，utils/json-parse.ts:2），配 repairJson 修复字符串内原始控制字符与非法转义。legacy function_call 单通道归一化为现代 tool_calls 格式，缓冲上限 256KB/1024 条防内存失控（providers/openai-completions-tool-calls.ts:7-29）；id-only 续流绑定同一字节状态防重复计数。乱序容错做得最细：text_delta 缺 event.index 时恢复索引或新建 block（anthropic-transport-stream.ts:1576-1589），早到事件进 deferred-event-buffer 保序（:81）。第三方厂商的 reasoning_content 兼容回放分支 + reasoning-tag partitioner 从正文切思考段（:1541-1577）。

重试决策集中在宿主层，replay-safety 优先

  • SDK 层重试关到 0（Anthropic SDK maxRetries ?? 0，providers/anthropic.ts:423），决策上移宿主 failover 分类器 classifyFailoverSignal。
  • replay 安全阀是其独有设计：两类错误码标记「不可重放」——provider 已产出输出后失败、dispatch 后结果不明——防止未知输出被二次执行（src/llm/utils/retry.ts:10-46）。
  • Retry-After 手写解析支持三种 HTTP-date 格式（IMF-fixdate/RFC850/asctime），含 RFC9110 两位数年份滚动规则（packages/ai/src/internal/retry-after.ts:30-80）。流断后续传有专项模块 openai-responses-continuation.ts 与 provider-compaction-replay.ts（opaque data 重放）。
  • SSE 解析错误有专项回归测试（anthropic.sse-parse-error.test.ts 等）；stop reason 双协议各自映射归一；终局 usage 恢复专项处理（terminal-usage 模块）。

8.2 缓存：把「前缀字节稳定」做成通用基础设施

  • 声明式界碑：系统提示用 HTML 注释 <!-- CACHE_BOUNDARY --> 显式切割 stable/dynamic 两段，stablePrefix 块带 cache_control、dynamicSuffix 不带；hook 覆盖的 prompt 无界碑时自动补一个；动态追加统一走「插到界碑后」的 API（utils/system-prompt-cache-boundary.ts:10-63、transports/anthropic-payload-policy.ts:146-190）。
  • deepest-stable-message 断点策略：从尾部向前找最近一条稳定 user 消息落断点；易变的 runtimeContextCarrier 载体消息被排除出候选，使最深断点锚在最后一条真正稳定的 turn 上；tool_result 作 fallback 载体；预算 messageCacheControlLimit=4（anthropic-payload-policy.ts:209-270、providers/anthropic.ts:1149-1179）。TTL 经 env OPENCLAW_CACHE_RETENTION=long 映射 1h。
  • 确定性归一化三件套：工具按 name 排序（locale 无关）、文本段落代理对消毒 + CRLF→LF + 行尾空白裁剪、capability ids 去重排序——把「同样逻辑内容产出同样字节」做成通用设施而非 per-provider 补丁（utils/prompt-cache-stability.ts:10-50）。
  • 时间信息放用户消息：会话重置 prompt 把当前时间行以 nowMs 参数化追加在用户消息里而非 system，不污染缓存前缀（src/auto-reply/reply/session-reset-prompt.ts:109-122）。
  • usage 校验最严格：快照必须 input/cacheRead/cacheWrite 三值齐才有效；写侧细分 ephemeral_5m/1h 两桶；多轮 iterations[] 取最后一次迭代为真实 context window——顶层字段是跨迭代累计计费值，直接用会算错窗口（providers/anthropic-usage.ts:42-95）。OpenAI 侧另有 prompt_cache_key 64 字符截断钳制（providers/openai-prompt-cache.ts:1-14）。

9. DeepSeek Harness（公开资料推理，低置信度）

DeepSeek 官方编程 harness 无公开源码，本节基于公开 API 文档与社区资料推理，置信度标注为低；结论仅供方向性参考。

推理 DeepSeek API 是标准 OpenAI 兼容 SSE（chat.completions chunk 形态），reasoning 模型经 reasoning_content 字段流式输出思考内容（与 Hermes 表格中「DeepSeek v4/Kimi 要求回传 reasoning_content」的怪癖互为印证）。缓存上是自动缓存派：服务端磁盘级前缀缓存，无需任何显式控制参数，命中部分按约 1/10 价格计费；usage 返回 prompt_cache_hit_tokens / prompt_cache_miss_tokens 二元组而非三桶模型（Hermes 的 fallback 表里专门兼容了这个字段形态，佐证其真实性）。流式语义上无 ping 心跳消费、重连依赖客户端整请求重放的公开实践与主流一致。作为对照样本的价值在于：它证明了自动前缀缓存在 API 层可以完全下沉为基础设施，客户端唯一要做的是别把前缀弄脏。

10. 深度对比：差异本质、兼容性陷阱、事实标准

10.1 差异的本质：三个正交的设计轴

八家的差异不是随机散布，而是三条设计轴上的三种选型组合：

  1. 「谁把字节流变成结构」：SDK 委托（Claude Code、OpenCode、Qwen Code）换来了维护成本趋近于零，代价是超时/重试语义受制于 SDK 的黑盒（OpenCode 干脆显式 maxRetries=0 再在会话层自建，就是对这种失控的补偿）；自研状态机（Codex、Grok Build、Hermes、OpenClaw）换来 per-provider 怪癖的精细修正能力（函数名重发、同 index 换 id、流中夹 error chunk），代价是每个新 provider 都要重新踩一遍坑。
  2. 「事件粒度多粗」：delta 级（Claude/Grok/Hermes/OpenClaw）保住打字机体验但必须自己解决 partial JSON；item 级（Codex 聚合到 output_item.done 才处理 function_call）直接消灭了 partial JSON 问题——这是「信任服务端缓冲」的架构表态，前提是上游 API 提供了 item 级事件。Gemini 协议（Qwen）走第三条路：协议本身就把工具调用做成完整对象，问题在协议层不存在。
  3. 「缓存谁来管」：显式断点派（Anthropic 生态五家）把缓存当客户端责任，于是长出了 latch、哨兵行、界碑、stable-prefix 注册表这一整族防御工事；自动前缀派（Codex/OpenAI 系、DashScope、DeepSeek）把缓存下沉为服务端基础设施，客户端只贡献一个路由亲和键。两派的分野完全跟随底层 API 能力，而非团队偏好。

10.3 已成为事实标准的行为

  • 整请求重放，无人续传：八家的模型流中断后全部重放整个请求，没有一家对模型 API 使用 Last-Event-ID 续传（Claude 的续传机制仅存在于 session ingress 桥接通道）。对网关的含义：中断一个流 = 上游重算一次全量 token，这正是缓存价值的放大器。
  • 指数退避 + 抖动是标配：所有实现都是 ×2 指数 + 10~25% 抖动；Retry-After 头普遍被尊重且优先于本地退避曲线。cap 各异：32s（Claude）/30s（Grok）/60s（Codex 连接）/5min（Qwen 限流）。
  • 空闲看门狗谱系 90–300s：Claude 90s（opt-in）、Qwen 240s、Codex 与 Grok 300s、Hermes 180s 应用层探测。共同点是都区分「请求级」与「流级」两类超时，且承认请求级超时不管流体。
  • 动态内容后置：无论哪一派，「把易变内容挪出缓存前缀」都已制度化——Codex 的 current_time_reminder developer 片段、Hermes 的 date-only 时间行、OpenClaw 的界碑后动态区、Claude 的 DYNAMIC_BOUNDARY 哨兵。这是跨生态最一致的工程共识。
  • 缓存三桶计费口径：input/cache_read/cache_creation 分开统计并分开乘单价已是头部客户端标配；「prompt_tokens 恒为全量、不做减法」（Grok 注释）与「adjustedInput = input − read − write」（OpenCode）两种口径并存，前者是原始值后者是展示值。

11. 对 CrewRouter 网关的落地建议

前提回顾：网关在 server/routes/api.js 完成 provider 选择 → proxy-pool.js 代理出口选择 → gateway:beforeUpstream 插件钩子 → 转发与流式回传；server/providers/anthropic.js:62-63 已读 cache_read/cache_creation 两字段，providers/openai.js:56 已读 cached_tokens，routes/user.js:66 的 usage_records 已有 cached_tokens 列并在 user/admin 统计里 SUM。以下按优先级给出十条建议。

  1. 缓存友好路由（最高优先级）：给代理池加亲和键。Codex 用 prompt_cache_key、OpenClaw 给 OpenAI 系做 cache key 截断钳制，证明「路由亲和键」已是公开模式；而多上游账号轮询是缓存杀手——同一个会话落到不同上游账号，前缀缓存必然 miss。落地：proxy-pool.js 的 getProxyAgent(provider) 增加 affinityKey 参数；api.js 从请求体提取亲和键（Anthropic 的 metadata.user_id、Responses 的 prompt_cache_key、或 system 前缀 hash），同键粘住同一出口账号。注意与现有 429 摘除逻辑共存：粘住的出口被摘除才漂移，漂移后固定到新出口而非回到轮询。
  2. 尊重 Grok Build 预留的「第四断点槽位」。其源码注释明言客户端只打 3 个断点、第 4 槽位留给网关（conversation/messages.rs:36-43）。落地：转发 Anthropic 协议时若检测到 body 中 cache_control 断点数 ≤3 且消息数较多，可在最后一条 user 消息上补一个 ephemeral 断点再上行——这是唯一一处网关可以主动「替客户端」优化缓存的位置；断点数已达 4 或落在 thinking 块上时绝不补（API 会拒）。
  3. 转换层保真 cache_control 并拆开计费口径。transforms/anthropic-to-openai.js:198-200 目前把 cached_tokens 映射为 cache_read 而 cache_creation 恒 0；openai-to-anthropic.js:216-236 把 read+write 合并回 prompt_tokens_details.cached_tokens。建议：①转换时不丢消息体内的 cache_control 标记（丢标记 = 上游自动缓存前缀错位）；②usage_records 增加 cache_write_tokens 列，把「读 0.1×/写 1.25×」的三桶口径带进计费——Hermes 的 per-model 缓存单价表（usage_pricing.py:123-380）可作为定价参照；③前端命中率面板用 SUM(cache_read)/SUM(prompt) 计算，但按 Hermes 的教训排除 MiniMax 类恒定底噪模型。
  4. 击穿归因检测器网关化。Claude Code 在客户端做 system/tools/beta-header hash diff 定位击穿原因（阈值 MIN_CACHE_MISS_TOKENS=2000）。网关视角更天然：同一亲和键的连续请求，对比 system 前缀与 tools 数组的 hash，命中率骤降时在管理端标注候选原因（system 变了/tools 变了/换上游账号了/TTL 过期了）。这能把「用户抱怨费用高」从猜测变成定位。
  5. 网关流式超时必须 ≥ 客户端看门狗。客户端 idle watchdog 谱系 90–300s（Qwen 240s/Codex 300s），若 api.js 的 UPSTREAM_TIMEOUT 小于它们，会出现网关先杀流、客户端把锅算给上游的假故障。建议：SSE 流式路径学 Hermes read=None 不设读超时，改用 ≥300s 的应用层 idle 探测 + 连续 N 次才判死；非流式路径维持现有较短超时。
  6. 等待首包期间向下游注入 SSE 注释行心跳。推理模型首 token 可达数分钟，NAT/LB 可能掐静默连接。所有客户端都不消费 ping 事件但 SDK 会吞掉 SSE 注释行（: keep-alive），Claude Code 的 stall 检测也只在真实事件到达后触发——因此注释行是安全的无害填充。落地：api.js 流式回传循环里每 15s 写一行 : ping\n\n，同时透传上游 Retry-After 头给下游（四家的退避逻辑都以它为最高优先级）。
  7. 错误页 content-type 纪律。Qwen Code 校验 text/event-stream 否则抛 NonSSEResponseError——网关自身的 401/429/502 若以 HTML 页返回给 /v1/messages 流式请求，客户端能识别为失败（好事），但要确保不会以 200 + HTML 返回；统一 JSON 错误体 + 正确 status code 即可同时满足所有八家的解析器。
  8. usage 归一层照抄 Hermes fallback 表。其 normalize_response_usage 兼容五种读侧字段形态与四级写侧 fallback（usage_pricing.py:1280-1379），网关作为多上游汇聚点必然遇到同样碎片化——把它移植成 providers 层的统一归一函数，下游 usage_records 就永远只存一种形态。
  9. 子代理流量识别为下一期铺垫。Codex 的 prompt_cache_key 里已编码 {source}:{parent_thread_id} 结构、Anthropic metadata.user_id 是现成的会话标识——本期发现的这些信号将在子代理归因报告中展开，建议 api.js 先把 prompt_cache_key/metadata 原样落库到 plugin_meta 或新增列，为归因分析留存原料。
  10. 把「字节稳定」写进网关自己的注入逻辑。inject_prompts 注入的内容会成为请求前缀的一部分：注入模板一旦变更，全部用户的缓存前缀集体失效。借鉴四家共识——注入内容放 system 尾部或消息区（界碑之后）、时间类字段日期精度封顶、模板版本号不进前缀、灰度发布按用户分批切换。

一句话总结

八家客户端花了两千行源码回答同一个问题——「如何让每一次请求的前缀与上一次逐字节相同」。网关站在比客户端更好的位置上：它看得见亲和键（谁该共享缓存）、握着路由权（谁能命中缓存）、摸得到断点预算（还剩几个空槽）。把这三件事做完，网关就从「流量管道」升级成了「缓存优化器」，而这是任何端侧客户端都做不到的。
