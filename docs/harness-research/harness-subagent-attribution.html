1. 总体概览：编排形态与归因信号两张矩阵

现代编程 harness 已经普遍长出了「主代理派活、子代理干活」的第二层执行结构。一次用户可见的主任务背后，是若干个独立计费的 API 会话：每个子代理有自己的消息数组、自己的 system prompt、甚至不同的模型。对网关来说这意味着两件事：① 流量放大——一次人工交互可能产生数十倍的上游请求；② 归因难题——这些请求在 HTTP 层长得像不像「一家人」，决定了网关能不能把它们记在同一本账上。

2. Claude Code（Agent 工具 + 父子共享 session_id 的归因盲区）

2.1 编排机制

工具名 Agent，旧线协议名 Task 作为 alias 保留兼容（src/tools/AgentTool/constants.ts:1-4、AgentTool.tsx:227）。参数：description/prompt 必填，subagent_type/model(sonnet/opus/haiku)/run_in_background 可选，多代理扩展参数 name/team_name/mode 与 isolation/cwd（AgentTool.tsx:81-107）。subagent_type 省略时按 fork 门控决定走 fork 或默认 general-purpose（:310-316）。

执行模型是全新 API 会话：普通路径下子代理的消息数组只有一条 createUserMessage({content: prompt})（AgentTool.tsx:537-540），以它为 initialMessages 起独立 query 循环（runAgent.ts:748-757）；父传子的全部内容 = 该 agent 定义自己的 system prompt 加环境详情增强（AgentTool.tsx:519-531）。例外是 fork 路径：子继承父的完整对话上下文与父已渲染 system prompt 的逐字节副本（源码注释明说这是为了缓存一致），消息由 buildForkedMessages 构造——克隆父 assistant 全部 tool_use、占位 tool_result、附每子指令，并插入 <fork_boilerplate> 标记（AgentTool.tsx:484-500,620-633、forkSubagent.ts:94-120）。

  • 模型解析链：env CLAUDE_CODE_SUBAGENT_MODEL > 工具参数 model > agent 定义 frontmatter > 继承父（默认 'inherit'）（src/utils/model/agent.ts:24-45）；内置 Explore 对外部用户固定 haiku。
  • 并发：无全局上限常量——并行方式是单条 assistant 消息里放多个 Agent tool use block（提示词明确要求这么做，prompt.ts:245-250）；仅批量技能 MAX_AGENTS=30、hook 场景 MAX_AGENT_TURNS=50；同步代理 120 秒后自动转后台（AgentTool.tsx:73-79）。
  • 结果回传：同步结束只返回单条总结消息（取最后一条含文本的 assistant 消息），工具提示词明说「结果对用户不可见」；后台完成经 task-notification 投递 finalMessage + token/tool 统计（agentToolUtils.ts:276-357、AgentTool.tsx:976-989）。
  • 嵌套：general-purpose 声明 tools:'*' 可再开子代理；内置 Explore 显式禁用 Agent 工具；fork 子内再 fork 被运行时守卫双保险拒绝（querySource 检查 + fork_boilerplate 消息扫描）；深度无专门计数器，靠每 agent maxTurns 封顶（FORK_AGENT maxTurns 200）。

2.2 归因：结构化信号为零，只剩指纹

核心发现——父子共享 session_id：每个请求都带 metadata.user_id，其值是一段 JSON：{device_id, account_uuid, session_id}（可被 CLAUDE_CODE_EXTRA_METADATA 追加，src/services/api/claude.ts:519-528）。但 session_id 来自 CLI 进程级全局 getSessionId()（src/bootstrap/state.ts:331,431-432）——父与所有子代理共用同一个值。也就是说网关即使完整解析 metadata，也无法从这一字段区分主任务与它的任何子代理。
  • 无 per-request 头差异：不存在标识 agent 类型的 HTTP 头或 beta header；beta 集合只随模型变化（getModelBetas）。
  • 最强识别信号是 system prompt 首句指纹：内置子代理均以固定句式开头——general-purpose「You are an agent for Claude Code…」、Explore「You are a file search specialist for Claude Code…」（built-in/generalPurposeAgent.ts:1、exploreAgent.ts:22）；主线程则是完整的主系统提示词。次级特征：普通子代理 thinkingConfig 被强制 disabled（fork 子除外，runAgent.ts:676-684）；fork 流量请求前缀与父字节一致且消息含 fork_boilerplate 标签（forkSubagent.ts:9-12）。
  • agent 类型只活在客户端遥测里：querySource = 'agent:builtin:<type>' | 'agent:custom'（src/utils/promptCategory.ts:19-27）；埋点 tengu_agent_tool_selected{agent_type, model} 走 OTel 一方日志——这些都不随模型请求出网。
  • usage 聚合不分家：成本在共享 API 层累加进全 session 全局状态（addToTotalSessionCost，src/cost-tracker.ts:278-296），每个子代理的 query 也走同一入口；/cost 只报总量 + 按模型分解，不按 agent 分。每子代理粒度的 token 只存在于后台任务 tracker 与 tengu_agent_tool_completed 埋点中；辅助设施有 Perfetto 追踪注册 (agentId, agentType, parentId)（runAgent.ts:355-364）。

3. Codex CLI（spawn_agent 多线程协作 + 全场最丰富的 HTTP 归因信号）

3.1 编排机制

Codex 把多代理做成了一组协作工具而非一次性派活：V2 为平铺 function spawn_agent（必填 task_name+message），配套 send_message / wait_agent / interrupt_agent / followup_task / list_agents 五件套（core/src/tools/handlers/multi_agents_v2/ 各文件；spec 定义 multi_agents_spec.rs:100-142）。全参数包括 message/task_name/agent_type/fork_turns/model/reasoning_effort/service_tier。

  • 独立 Session/thread：codex_delegate 新建 Session::spawn，独立 rollout 与上下文管理器，审批策略强制 never（core/src/codex_delegate.rs:60-135）。
  • 默认 fork 继承：fork_turns 默认 "all" 继承父全部轮次（FullHistory），可为 none 或 N；full-history fork 且未指定 role 时继承父 developer_instructions；继承条目有裁剪规则（multi_agents_v2/spawn.rs:126-141,280-315、agent/control/spawn.rs:52-90）。这与 Claude Code 的「默认全新会话」正好相反。
  • 父子显式传参：session_source = SubAgent(...)、parent_thread_id、thread_source=Subagent 显式传入（codex_delegate.rs:84-110）；user_instructions 从父继承。
  • 并发双层控制：配置 agents.max_concurrent_threads_per_session 默认 6（DEFAULT_AGENT_MAX_THREADS，config/mod.rs:225）；注册表槽位 reserve_spawn_slot 超额报 AgentLimitReached + 运行时限流器仅作用于 V2 SubAgent（agent/registry.rs:96-110、agent/control/execution.rs:46-98）。槽位需 close_agent 显式释放（completed 也占位）。
  • 结果回传双向：子线程事件流经 forward_events 转发；父用 wait_agent 收割最终态 Completed(final assistant message)；状态变化以 <subagent_notification> 用户角色片段注入父对话，过程进度落 TurnItem（protocol/src/protocol.rs:1748-1760、context/subagent_notification.rs:29-44）。
  • 嵌套深度显式建模：SessionSource::SubAgent(ThreadSpawn{parent_thread_id, depth, agent_path, nickname, role})，子深度 = 父深度+1，超限判断配 agents.max_depth（protocol.rs:2587-2680、registry.rs:79-93）。

4. Grok Build（task/spawn_subagent + 头部直通子会话 ID）

4.1 编排机制

规范工具名 task，同时接受 Task/spawn_subagent 三种拼写（xai-grok-tools/src/implementations/grok_build/task/mod.rs:180-188）；编排器预设会把工具改名为 spawn_subagent、参数 run_in_background→background（xai-grok-agent/src/config.rs:149-157）。参数：prompt/description/subagent_type/run_in_background(默认 true)/isolation/resume_from/cwd/model/task_id（xai-tool-types/src/task.rs:14-59）；内置子代理三种 general-purpose/explore/plan。

  • 完全独立子会话：child_session_id = 子代理的 uuid v7，新建持久化目录与 chat state（subagent/handle_request.rs:459-462,640-652）。上下文三来源 New/Forked/Resumed——Forked 把父历史作 <background_context> 注入，但模型发起的 spawn 固定 fork_context:false 即全新消息数组（subagent/mod.rs:53-62、task/mod.rs:550）。
  • 父传子四件套：任务 prompt + persona 指令（system-reminder 形式）+ role prompt + agent 定义 prompt_body；子代理用独立的紧凑系统提示模板（PromptAudience::Subagent，非父模板），启动提示携带 is_subagent:true / parent_session_id / subagent_type（handle_request.rs:505-520,986-992,1085、prompt/template.rs:49-50）。
  • 模型解析三级：runtime override > agent 定义 model > 父模型兜底；resume 时强制钉住源模型忽略调用方覆盖；另有 [subagents] 级 model_overrides 配置（handle_request.rs:388-420,169-181、subagent_coordinator.rs:385-390）。
  • 并发上限 32 全场最高：DEFAULT_MAX_CONCURRENT=32，env GROK_MAX_CONCURRENT_SUBAGENTS 可调，超限行为可配 queue|fail（默认排队）；前台等待预算 600s 超时自动转后台（task/admission.rs:6,41-58,104-127、subagent_coordinator.rs:168-173）。
  • 结果回传双通道：阻塞模式返回 SubagentCompleted{output, subagent_id, tool_calls, turns, duration_ms} 直接进父对话工具结果；后台 fire-and-forget + 完成后向父会话注入 system-reminder（轮次间缓冲投递）；ACP 事件 SubagentSpawned/Finished 含 tokens_used 提供中途可见性（task/mod.rs:553-661、reminders/task_completion.rs:411-497、notification.rs:1686-1710）。
  • 防递归靠剥工具：MAX_SUBAGENT_DEPTH=1，depth 达上限时直接从子的工具集中剥离 task 工具（而非运行时报错）；嵌套 spawn 重挂到根会话（task/mod.rs:36-46,365-373、coordinator/spawn.rs:110-152）。

4.2 归因：HTTP 头直通子会话实例 ID

Grok Build 的每个采样请求固定携带 8 个自描述头：x-grok-conv-id / x-grok-req-id / x-grok-model-override / x-grok-session-id / x-grok-agent-id 及可选 x-grok-turn-idx/-deployment-id/-user-id（xai-grok-sampler/src/client.rs:49-78）。关键事实：子代理请求的 x-grok-session-id 与 x-grok-conv-id 都取子会话自身的 uuid（session/acp_session_impl/turn.rs:2290-2320、xai-chat-state/src/actor/request_builder.rs:101）——网关凭这一个头就能把请求精确归因到具体的子代理实例，并与父会话及其他兄弟子代理区分。两个限制：x-grok-agent-id 是进程级常量无区分度；父子关系不在 HTTP 层表达——它落在磁盘 SubagentMeta（parent_session_id 写入父会话目录 subagents/<id>/）与 GCS trace 元数据（parent_prompt_id/depth/isolation_mode）中（handle_request.rs:518-580）。

辅助指纹：子模板首句固定「You are a Grok Build subagent — a focused worker delegated a specific task.」（templates/subagent_prompt.md:1）；子代理被剥离 ask_user_question 工具造成 tools 数组形状差异（subagent_coordinator.rs:52-54）。

usage 聚合是全场唯一有「回写父账本」设计的：从子会话 chat-state 账本取 by-model 用量后，通过 SessionCommand::RecordSubagentUsage{by_model, parent_prompt_id, incomplete} 回写父会话；父侧折账归属当前 prompt 或仅 session 级（嵌套欠账有 sticky 标记防丢）；遥测事件 SubagentLaunched/SubagentLimitHit 记录编排行为（subagent/attempt_runner.rs:266-333、run_loop.rs:1094-1120、updates.rs:147-174、handle_request.rs:944-953）。

5. OpenCode（task 工具 + 网络层同质化，归因最难）

5.1 编排机制

工具名固定 task（packages/opencode/src/tool/task.ts:19），参数 description/prompt/subagent_type/task_id(恢复旧子会话续跑)/command/background。内置 subagent 型 agent 只有 general 与 explore（mode:"subagent"，agent/agent.ts:180-217），用户 config 可增删改。执行模型：sessions.create({parentID}) 创建全新子会话并跑完整 SessionPrompt 循环，父只传任务 prompt（task.ts:158-212）；权限派生自父会话 deny 规则与子 agent 自身规则合并。系统提示组装顺序：[agent.prompt 有则整体替换 provider 基础提示] + env + instructions + mcp + skills（session/llm/request.ts:57-66）。

  • 模型选择：子 agent.config 可配 model，否则继承父 assistant 消息的 modelID/providerID；variant 仅在未显式指定模型时继承父值（task.ts:178-210）。
  • 并发无数值上限：同一助手消息内多个 tool call 以 concurrency:"unbounded" 并发等待，即可并行发多个 task；后台子代理需 OPENCODE_EXPERIMENTAL_BACKGROUND_SUBAGENTS=true 实验开关（processor.ts:571-575、effect/runtime-flags.ts:43）。
  • 结果回传：前台等待完成后把最终 text 包成 <task id=… state="completed"><task_result>…</task_result></task> 进父对话；后台完成以 synthetic 文本 part 注入父会话；tool part metadata 暴露 parentSessionId/sessionId/model/background/jobId，且子会话本身是独立可见的会话行（task.ts:67-78,186-199,229-258,330-347）。
  • 嵌套双保险：沿 parentID 链计算深度，≥cfg.subagent_depth(默认 1) 即拒绝；子会话权限默认 deny task/todowrite 除非子 agent 显式允许（task.ts:105-118、agent/subagent-permissions.ts:17-23）。

5.2 归因：八家中网络层最同质的一家

核心发现：OpenCode 的模型请求经 Vercel AI SDK 发出，headers 只来自 provider 配置——没有任何子代理或会话专用 HTTP 头（session/llm/request.ts:84-100）。唯一的会话标识在 OTel 遥测层（experimental_telemetry.metadata.sessionId = 子会话自身 id，functionId="session.llm"），但遥测是否出网取决于导出配置，不进请求体/头（llm.ts:344-351）。父子关系只存在于本地 DB 的 session 行 parentID 字段，完全不出网。

仅存的启发式信号：① 子 agent 若有专属 prompt 会替换基础提示（如 explore.txt）；② 环境块固定句式 "You are powered by the model named …"；③ 子会话历史全新——首条 user 即任务 prompt、历史短，与主会话的长前缀形态截然不同；④ 权限 deny 导致 tools 数组缺 task/todowrite 定义。usage 聚合：每条 assistant message 流式累计 cost/tokens 后持久化到会话行的 tokens_* 列（归一化含 cache read/write 分层计价），但父会话不汇总子代理用量——子用量记在子会话自己的行上，task 工具只回传文本（session/session.ts:97-144,341-403、processor.ts:444-454）。

6. Qwen Code（Agent 工具 + promptId 内嵌子代理复合键）

6.1 编排机制

内置 Agent 工具，参数接口相当宽：prompt/description/subagent_type/model/fork_turns/fork_tools/fork_profile/run_in_background/name/isolation:'worktree'/working_dir（packages/core/src/tools/agent/agent.ts:206-250,668）。子代理定义来自 frontmatter 文件或内置注册表，默认 general-purpose，另有 Explore/statusline-setup/review 等。特色是 name 参数经 TeamManager 派生常驻队友——队友必并发、经团队消息汇报（agent.ts:224-227,829）。

  • 上下文：常规子代理与队友不继承父会话历史（headless 独立 Config 与工具注册表）；仅 subagent_type:"fork" 继承父对话，可选最近 N 个真实用户轮次 fork_turns；fork 的系统提示直接写明 "Do not spawn sub-agents"（agent.ts:858、tools/agent/fork-subagent.ts:29-32,218-251）。
  • 模型选择走「档位」制：model 参数是 grade 经 subagentManager.resolveModelGrade 解析；带显式 model 的自定义代理不可被覆盖；缺省 inherit 时回落到父当前模型（agent.ts:2594-2682、subagents/subagent-manager.ts:147-166）。
  • 并发两层限制：后台子代理全局上限 DEFAULT_MAX_CONCURRENT_BACKGROUND_AGENTS=10（env QWEN_CODE_MAX_BACKGROUND_AGENTS 可调）+ 按模型 ID 的每模型 cap 映射；满员排队等槽；终态保留上限 MAX_RETAINED_TERMINAL_AGENTS=32（agents/background-tasks.ts:50-148、agent.ts:2699-2719）。
  • 结果回传：顶层后台子代理终态以 task-notification 注入父对话——注释称其为「父方唯一回传通道」；前台内联返回 llmContent + returnDisplay(task_execution)；模型可见结果经 toModelVisibleSubagentResult 剥离 analysis 块（background-tasks.ts:15、agents/subagent-result.ts:19-60）。
  • 防递归三道闸：后台委派 v1 仅限顶层——嵌套调用中显式 run_in_background:true 被运行时守卫拒绝、隐式请求降级为前台同步；fork 提示禁再 spawn；read_only 队友的执行允许表屏蔽 nested agents（agent.ts:2630-2643,290-297）。

6.2 归因：把身份编进每次请求的 promptId

Qwen Code 没有专用 HTTP 头，但有一个精巧的设计：每次 LLM 请求的 promptId 复合键 = ${sessionId}#${subagentId}#${promptOrdinal}，其中 subagentId = ${name}-${randomPart}（agents/runtime/agent-core.ts:883,922,463）。loop 检测器同样以 sessionId#subagentId 作键。这意味着网关从请求体提取 prompt-id 类字段后，按 # 切分即可得到「父会话 / 哪个子代理实例 / 第几个请求」三元组——归因信息随每个请求自然出网，不需要额外协议支持。运行时事件（compact、finish 等）也统一携带 subagentId 字段。

system prompt 指纹：无统一机器标记，但内置代理各有固定提示词开头，如 general-purpose 的 "You are a general-purpose subagent working for a parent agent"（subagents/builtin-agents.ts:54）。usage 聚合：每个子代理运行实例持有独立统计对象（input/output/thought/cached/totalTokens + 工具级用量，runtime/agent-statistics.ts:24-43）；本次检索范围内未见把子代理 token 回写进父会话账本的路径——与 Grok Build 的主动回写形成对比。

7. Hermes（delegate_task + 协议层父子链路与逐子代理成本核算）

7.1 编排机制

工具名 delegate_task，注册于 delegation 工具集（描述 "Spawn subagents with isolated context"），参数 goal/context/tasks[]/role(leaf|orchestrator)/output_schema/action(spawn|list|steer|stop)/subagent_id/message（toolsets.py:300-301、tools/delegate_tool.py:4730-4921）。模块 docstring 明示执行模型：「fresh conversation (no parent history)、own task_id、inherit parent toolsets、focused system prompt」，父上下文只见委派调用与汇总结果。

  • 硬性剥夺清单：DELEGATE_BLOCKED_TOOLS = {delegate_task, clarify, memory, send_message, cronjob}——子代理天然不能再委派、不能反问用户、不能动记忆（:49-56）；子系统提示固定开头 "You are a focused subagent working on a specific delegated task."（:1191）。
  • 跨供应商路由能力：单任务 model 参数覆盖否则继承父；delegation 配置可整体 override provider/base_url/api_key/max_tokens——即子代理可以整体路由到另一个便宜供应商（如 OpenRouter），这是八家中唯一把「子代理换供应商」做成一等配置的（:1587-1609,1755,1891-1898）。
  • 并发默认 10：delegation.max_concurrent_children 可调（仅设下限 1，>10 打一次性成本告警）；单轮超额 delegate 调用被截断到上限；每子代理独立迭代预算 max_iterations 默认 50（:122,846-928,1737-1740、run_agent.py:4960-4978）。
  • 整批聚合回传：fan-out 作为异步单元 join 全部子代理后产出一个合并 results 块作为单条消息重新进入对话；不支持异步投递的会话降级同步或经自 POST /v1/chat/completions 带 X-Hermes-Session-Id 头唤醒原会话；每子代理有 append-only 实时日志文件（:4080-4125、delegation_live_log.py:5-13）。
  • 递归显式授权制：默认 MAX_DEPTH=1 孙代拒绝；role='orchestrator' 才加回 delegation 工具集，深度超限时 role 自动降级 leaf；谱系校验辅助 _is_descendant_of/_resolve_session_lineage/_owns_subagent_record（:129-132,1617-1701,380-426）。

7.2 归因：进程注册表 + 协议层父子字段 + 逐子代理成本

  • 稳定 ID 体系：每个子代理获得 sa-{task_index}-{uuid4.hex8}，嵌套时记录 parent_subagent_id 与 tui_depth；进程级归因注册表 get_subagent_attribution 由终端 task_id 反查 {subagent_id, goal, delegation_id}（活跃 + 近期 FIFO 上限 200）——子代理启动的后台进程天然携带此 ID（delegate_tool.py:157-190,1630-1632）。
  • HTTP 头：X-Hermes-Session-Id 为 API 会话绑定头——后台批次完成后以此自 POST 唤醒源会话，意味着子代理完成事件可通过该头归因回源（:4106-4110、run_agent.py:352）。
  • TUI/gateway RPC 协议有专门委派方法：delegation.status 返回 active 列表/paused/max_spawn_depth/max_concurrent_children，active 记录字段 {subagent_id, parent_id, depth, goal, model, started_at,…}——协议层直接暴露完整父子链路（tui_gateway/methods_session.py:3253-3305、delegate_tool.py:356-360）。
  • usage 是全场最细粒度：account_usage.py 记的是账户配额维度（Codex 5h 窗口/Anthropic OAuth/OpenRouter credits 等）而非 token 归因；真正的归因在 delegate 结果条目里——每子代理记录 tokens{input,output}（取自 child session 计数）、api_calls/duration/model/exit_reason/truncated/tool_trace，以及 cost_usd 折算进父会话总开销（_child_cost_usd 序列化前剥除，移植自 kilocode#9448）（delegate_tool.py:3079-3130、agent/account_usage.py:26-45）。注意一个易混点：kanban worker 以 env HERMES_KANBAN_TASK 标记且被从 delegate 子进程剥离——它是另一种后台形态，不占用委派并发额度。

8. OpenClaw（sessions_spawn + 自描述会话键与血统元数据）

8.1 编排机制

工具名 sessions_spawn（"Starts subagent or ACP-backed sessions with inherited tool policy and delivery context"），参数矩阵是八家最宽的：task/taskName/label/runtime(subagent|acp)/agentId/model/runTimeoutSeconds/thinking/cwd/mode(run|session)/cleanup/sandbox(inherit|require)/context(isolated|fork)/lightContext/collect/outputSchema/groupId/attachments/resumeSessionId（src/agents/tools/sessions-spawn-tool.ts:62,130-260）；配套 subagents（列表/控制）、sessions_yield、agents_wait/list 工具。

  • 会话键即身份：mintSpawnSessionKey 铸造 agent:<targetAgentId>:subagent:<uuid>（incognito 变体替换为 :subagent:incognito-）；context:"fork" 仅拉取 requester transcript 且要求同 agent；父传子上下文写进子系统提示——任务 + [Subagent Task] + requester 会话键/渠道 + 自己的会话键（spawn-plan.ts:51-57、subagent-spawn-child-plan.ts:194-200、subagent-system-prompt.ts:95-108）。
  • 并发双层：子代理并发默认 DEFAULT_SUBAGENT_MAX_CONCURRENT=8（顶层 agent 并发按 CPU 数钳制在 8..16）；每 agent 直系子代默认 5，经 resolveChildAdmission + countActiveRunsForSession 准入（config/agent-limits.ts:3-48、spawn-plan.ts:22-23）。
  • 推送式结果回传：子系统提示明文规定 "Finish: final auto-reported to <parent>"、"Results auto-announce to you, not main"——完成后由 completion/announce 管线投递给 requester，禁止轮询；终态写信号日志且 watcher=requester；swarm 用 JSON Schema 校验结构化收集结果（subagent-system-prompt.ts:55,76-77、sessions/session-state-events.ts:1029-1057）。
  • 深度用会话键计数：DEFAULT_SUBAGENT_MAX_SPAWN_DEPTH=1，深度 = 数会话键中 :subagent: 出现次数，超限直接 forbidden；子系统提示按 canSpawn 分支，depth≥2 输出 "Leaf worker: cannot spawn"；cron 也拒收 subagent 目标防异步递归（session-key-utils.ts:323-344、cron/service/wake.ts:56）。

8.2 归因：内部最结构化的血统体系

  • 执行血统元数据：spawn 时构造 withAgentRuntimeExecutionLineage{relation:"sessions_spawn", requesterRef/controllerRef/depth}，并对 spawn-depth/sandbox/inherited-tool/target 各策略做 sha256 指纹引用——不仅记录「谁生了谁」，还记录「继承了什么策略」（subagent-spawn-execution-identity.ts:15-58）。
  • 状态事件显式记父子边：recordSubagentSpawned 写 kind:"child_spawned"、actorType:"agent"、actorId=requesterSessionKey（父）、watcherSessionKeys=[requester]、去重键 child-spawned:<runId>；终态 run_completed/run_failed 同样挂 watcher；注册表持久化 requesterSessionKey/requesterOrigin/requesterDisplayKey（session-state-events.ts:1010-1057、registry/subagent-registry.types.ts:45-47）。这套事件流本身就是审计日志。
  • usage 消息级随 transcript：assistant 消息携带 usage{input,output,cacheRead,cacheWrite,totalTokens,cost{input,output,cacheRead,cacheWrite,total}}；一个值得抄的细节：自动化回写（cron 等）使用全零 usage + model:"automation-result" 溯源标记，避免机器流量污染真实用量统计；注册表维度只记时间与结局不聚合 token（sessions/background-session-result.ts:20,99-119）。
  • 对外可见性说明：visible=true 的 spawn 走 dashboard 持久会话路径；对外 HTTP 层的归因信号取决于部署形态（Gateway 内部路由用自描述会话键），纯 API 观察者仍可靠系统提示固定标记 # Subagent Context 与 [Subagent Task] 辨认。

9. DeepSeek Harness（公开资料推理，低置信度）

DeepSeek 官方编程 harness 无公开源码与文档描述其多代理机制，本节置信度标注为低。

推理 公开渠道未见 DeepSeek harness 有 Task/spawn 类子代理工具的证据；其官方 CLI 形态更接近单代理循环 + MCP 扩展。若存在内部多代理实现，参考其 API 生态（OpenAI 兼容）大概率不会超出本报告 Codex/OpenAI wire 的信号模式（thread/session 元数据 + 自动前缀缓存亲和键）。作为横向对照的价值：八家里有两家（Claude Code、OpenCode）已经证明了「没有结构化归因信号」是真实存在的常态，网关设计不能假设所有客户端都会配合。

10. 深度对比：归因信号强弱排序与事实标准

10.1 归因信号强弱排序（网关可提取性视角）

排名客户端网关单凭一次拦截能拿到什么还差什么
1Codexx-openai-subagent 判定「是子代理」→ thread_id 定位实例 → parent_thread_id 回连父 → agent_name 读角色名。四问全能答。无

3OpenClaw系统提示 # Subagent Context/[Subagent Task] 标记 + 会话键格式（Gateway 部署可见）。血统元数据在内部事件流，外部观察者拿不到 depth/requesterRef 全貌

10.2 差异的本质：归因信号是副产品，不是设计目标

为什么 Codex/OpenClaw/Hermes 的信号这么全而 Claude Code/OpenCode 几乎没有？规律很清晰：归因信号的丰富度跟随客户端自身的需求——Codex 要做六件套协作（wait/interrupt/list 必须有稳定句柄）、OpenClaw 要做推送式 announce 与审计（必须记 requester 边）、Hermes 的 delegation 是产品级功能（要 pause/steer/status），这些能力倒逼出结构化身份体系。反过来，Claude Code 的子代理是一次性的 fire-and-forget 派活（结果就一条总结消息），进程内 ALS 遥测够用，自然没有为网络层归因做任何事。给网关的启示：不要期待客户端「配合归因」，要设计一个对最弱信号（Claude Code/OpenCode 形态）也兜得住的分类体系，把强信号当增益而非前提。

10.3 已成为事实标准的行为

  • 独立子会话无一例外：八家全部是「新消息数组从零开始」模型，没有任何一家让子代理增量读写父对话；fork（整段继承）只是复制快照的语法糖。对网关意味着：每个子代理的第一个请求都是一次冷启动的全量前缀计费（fork 场景例外——Claude/Grok/Qwen 的 fork 都刻意保持前缀字节一致以命中缓存，这又回到了上一期缓存报告的主题）。
  • 默认深度 1：除 Claude Code general-purpose 与 Hermes orchestrator 显式授权外，所有实现默认禁止孙代；且主流防递归手段是「剥工具」而非运行时报错。
  • 子代理默认继承父模型：全部支持覆盖但缺省都是 inherit；「便宜模型跑子代理」是配置项而非默认值。
  • 结果压缩成单条消息回传：无论过程多少轮，回到父对话的都是一条总结（Hermes 是整批合并成一块）。父上下文永远不会被子代理的过程膨胀。
  • 并发上限谱系 6–32：Codex 6 / OpenClaw 8 / Qwen·Hermes 10 / Grok 32；一次主任务的请求放大倍数 = min(并发, 任务数) × 每子代理轮数，网关容量规划应按此估算而非按人工交互频率。

11. 对 CrewRouter 网关的落地建议

前提回顾：server/routes/api.js 是唯一转发出口，usage_records 已有 request_source/user_agent/plugin_meta 列，routes/client-events.js 的 client_events 表已带 harness/session_id/tool_name 维度，routes/stats-report.js 已有客户端上报通道。以下按优先级给出八条建议。

  1. 在 api.js 建立统一的归因字段提取层（最高优先级）。转发前对请求做一次「归因体检」，结果落 usage_records 新增 JSON 列（或先塞进现有 plugin_meta）：① Anthropic wire → 解析 metadata.user_id 内嵌 JSON 取 session_id/account_uuid；② OpenAI Responses wire → body 的 client_metadata.thread_id/parent_thread_id/root_turn_id/agent_name；③ 任意 wire → 扫自定义头 x-codex-parent-thread-id、x-openai-subagent、x-grok-session-id、X-Hermes-Session-Id；④ 任意 wire → 提取 prompt-id 类字段按 # 切分（Qwen 形态）。这一步不改任何转发行为，纯观测，风险最低收益最大。
  2. 定义「逻辑任务」聚合模型。账本顶层单位不应是请求也不应是 API key，而是「一次主任务 = 父会话 + 其全部子会话」。父子边的建立优先级：parent_thread_id（Codex，精确）> x-grok-session-id 与父会话的时间邻近配对（Grok，需启发式）> promptId 前缀共享（Qwen）> 同 session_id 内 system 指纹突变（Claude Code，只能聚不能拆）> 无信号按 key+时间窗（OpenCode）。管理端先按此模型出「任务视图」，再谈按任务限额。
  3. 内置 system prompt 指纹分类器作兜底。本期收集的五条固定句式可直接做成特征库：「You are an agent for Claude Code」「You are a file search specialist for Claude Code」「You are a Grok Build subagent」「You are a focused subagent working on a specific delegated task」「# Subagent Context / [Subagent Task]」，外加两个形态特征：普通子代理 thinkingConfig disabled、首条 user 消息即完整任务 prompt 且历史极短。分类结果标注置信度入库，强信号出现时反向校正指纹库。
  4. 用量报表打「子代理流量占比」指标。三家客户端的报表都有盲区——Claude /cost 不分 agent、Codex 不合并父子、OpenCode 不汇总子会话——网关恰好站在能看到全局的位置。建议在 admin/user 统计里增加：子代理请求数与 token 占比（凭第 1 条的提取结果）、平均每逻辑任务的请求放大倍数。这个数字对用户理解账单、对网关做容量规划都是刚需。
  5. 限流与配额按逻辑任务设计。一次主任务的突发 = 子代理并发（业界默认 6~32）× 多轮迭代，瞬时 RPS 可能是单人交互的数十倍。现有按 key 的限流会被单个重度用户的并行 spawn 打满，误伤同 key 其他用途；建议配额维度加「每逻辑任务并发子会话数」软限制，超限时排队而非拒绝（对齐 Grok 的 queue 行为）。
  6. 透传保真：归因与缓存字段一个都不能丢。转换层（providers/transforms/*.js）改写 body 时必须原样保留 metadata.user_id、prompt_cache_key、client_metadata——前者是本期归因的原料，后者是上期报告证明的缓存路由亲和键。同理自定义头不要在转发时剥离。
  7. 网关自身发起的调用打零用量标记。借鉴 OpenClaw 的 automation-result 模式：fusion 面板（panel-runner/judge-analyzer/synthesizer）与后续任何 LLM 审计调用，在 usage_records 里用专用 request_source 标记并视情况不计费或单独计费，避免机器流量污染用户账单与命中率统计——这与第 4 点的占比指标互为补充。
  8. 为「fork 流量」做缓存感知的特殊记账。Claude Code fork 子代理的请求前缀与父逐字节一致、Codex fork_turns 继承父历史——这类请求天然高缓存命中，若按裸 input tokens 计费展示会让用户以为成本爆炸。结合上期报告的三桶口径，任务视图里对 fork 流量单独标注「继承前缀命中」，展示 adjusted 口径而非原始口径。

一句话总结

八家客户端在子代理编排上已经收敛出稳定范式（独立会话、深度 1、继承父模型、单条回传），但在「要不要让网络层知道这是谁」上分成泾渭分明的两派。CrewRouter 作为传输层，恰好是唯一能把两派流量放进同一本账的位置——先用强信号建精确链路，再用指纹库兜住弱信号，最后把「逻辑任务」做成计费与限流的原子单位，这三步做完，网关对多代理时代的可观测性就超过了任何单一客户端自己的报表。
