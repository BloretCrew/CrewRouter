1. 先给结论：请求语义分类与证据等级

网关收到的 HTTP 请求不能仅按 endpoint 或 User-Agent 理解。对同一个客户端，用户发一条消息、模型调用工具、后台子代理、压缩上下文和生成标题都可能复用同一 API 路径。最稳妥的做法是：先识别客户端来源，再用请求头、请求体、system prompt、模型/参数和相邻时序组合出请求语义，最后把判定结果与证据保存到 usage_records.plugin_meta，而不是把启发式结果覆盖到基础的 request_type（现有 api.js 在响应 finish 时仅按 path 记 responses/anthropic/chat）。

请求语义触发者典型外观网关判别信心
主对话用户直接发消息，模型继续当前回合完整 system/tools；最近一条 user 消息是自然语言；之后可能有工具调用和多轮 follow-up高（组合信号）
子代理主代理的 Agent/Task/spawn 工具专用父子头、thread/session 复合键，或独立 subagent system prompt；通常是新会话或 forkCodex/Hermes/OpenClaw 高；Claude/OpenCode 低
标题客户端为会话列表生成短标题短历史或首条 user 内容；无工具；短输出；常用专用 title/summary agent 或小模型。公开源码证据不均匀中到低，须校准
压缩/摘要窗口接近上限、手动 compact，或 overflow 救援极简/空 system、无工具、单条很长 user，正文含 serialized history / previous conversation / role 标记；或专用端点/头OpenCode/Codex/Grok 等；通用启发式中
重试/恢复429、超时、断流、prompt-too-long 或上游临时错误短时间内同一 session/thread、相同或近似 body 重发；可能带 retry header 或相同 idempotency/cache key时序+请求指纹较高
计划/评审plan mode、review/guardian、用户显式审查命令system/agent prompt 有 plan/review/guardian 指纹；模型、工具集合或权限策略发生变化中，依客户端而定
心跳/探测连接保活、能力探测、空闲唤醒空或极短 body、无正常 user 消息、固定 endpoint；有时根本不调用模型低，需结合访问日志
其他自动化缓存预热、索引、后台通知、目标摘要固定 system prompt、极短输入或结构化输入；常紧跟主请求或会话事件需要客户端专属规则
核心原则：「没有工具 + 单条长 user」可以标记为疑似压缩，但不能直接把所有短请求归为标题。标题、压缩和 review 都可能使用短历史；必须保留 reason_codes 与 confidence，允许后续用真实流量校准。

2. 通用请求类型与判别顺序

2.1 推荐的判别流水线

① endpoint / HTTP method
→ ② 客户端来源（request-source.js）
→ ③ 强语义头与结构化 body 元数据
→ ④ 专用 endpoint、system prompt、agent/tool 结构
→ ⑤ body 大小、token 参数、模型与请求时序
→ ⑥ 与同 session/thread 的前后请求比对
→ ⑦ 输出 request_semantics + confidence + reason_codes

当前代码已经具备两块可复用基础：extractAttribution() 可提取 Codex/Grok/Hermes 等头和 body 归因字段；classifyCompaction() 已实现「无工具、system 极短、单条 user、长历史痕迹」启发式（server/utils/attribution.js:30-56）。本报告不要求改运行时代码；以下是文档层面的分类规格。

2.2 信号优先级

优先级信号说明
1专用 endpoint / header / 显式类型字段例如 OpenCode POST /session/:id/summarize、Codex x-openai-subagent 的 compact/review、OpenClaw 内部 session key。可直接给高置信度。
2结构化父子或会话 IDCodex 的 client_metadata.thread_id/parent_thread_id、Qwen 的 promptId=session#subagent#ordinal、Hermes 的 X-Hermes-Session-Id。
3system prompt / agent prompt 指纹标题、压缩、plan、subagent 通常有专用模板；必须使用完整短语或结构组合，不要使用裸 system-reminder、CLAUDE.md 这类跨产品弱特征。
4消息形状与参数工具是否存在、消息数量、是否单条超长 user、max_tokens 是否很小、是否要求 JSON/XML、模型是否为廉价小模型。
5时序与重复指纹紧跟主请求、相同 body 重发、同一 thread 的短间隔请求可支持判断，但单独不能定类。

2.3 语义字段建议

plugin_meta.request_semantics = {
  type: "primary|subagent|title|compaction|retry|plan|review|heartbeat|other",
  confidence: "high|medium|low",
  reason_codes: ["header.x-openai-subagent=compact", "single_long_history_user"],
  parent_request_id: "...",       // 若能在网关内关联
  session_key: "...",             // 脱敏后的 thread/session key
  is_billable_business: true,
  is_maintenance: false,
  classifier_version: "2026-08-28"
}

语义分类应与 API 格式字段分离：request_type=responses|anthropic|chat 仍表示协议入口，request_semantics.type 表示业务含义。标题和压缩是否计费由策略层决定，分类器只负责记录事实与置信度。

3. 八家客户端逐一分析

3.1 Claude Code

类型可观察信号结论

标题公开报告材料没有足够源码证据确认独立 title API 或固定 title prompt。未知/待抓包，不要把短请求默认判成标题。
压缩请求前 autocompact；实验性 prompt-too-long 反应式通道；压缩请求可复用主模型缓存。见 src/query.ts:399,449、services/compact/autoCompact.ts:61。压缩 body 的通用形状可命中现有 classifyCompaction()。中到高：若出现单条长历史 user 且无工具，标记疑似 compaction。

标题证据等级：低。Claude Code 的子代理和压缩证据来自既有源码考古；标题生成若存在，需从实际网络日志确认。

3.2 Codex CLI

类型可观察信号结论
主对话Responses 请求，普通 thread metadata；完整工具和环境上下文。无特殊标记时默认类型。
子代理x-codex-parent-thread-id、x-openai-subagent=collab_spawn；body 的 client_metadata.thread_id/parent_thread_id/parent_turn_id/root_turn_id；turn metadata 有 subagent_kind/thread_source。见 core/src/client.rs:148,151,621-657、responses_metadata.rs:280-395。高：三重冗余，可按 thread_id 分账。
标题现有材料未确认独立 title 请求。Codex 有服务端/客户端多种维护调用，不能用 source 或小输出单独推断。待验证。
压缩x-openai-subagent=compact；可能是 remote /responses/compact 或 local compact。压缩实现包括 token-budget、remote v1/v2、local，见 core/src/compact.rs、compact_remote_v2.rs。高：专用 header 优先。
review/planx-openai-subagent=review 或 guardian/review session；thread source、agent path 和权限策略发生变化。高（有 header 时）。

3.3 Grok Build

类型可观察信号结论
主对话x-grok-session-id、x-grok-conv-id、turn index 等固定头；主 system 含 Grok Build 身份和 <user_info>。固定头用于会话定位，不等于子代理。
子代理子会话自身 uuid 在 x-grok-session-id；system 含「You are a Grok Build subagent」；父关系主要在本地 SubagentMeta/GCS trace 的 parent_prompt_id/depth，不一定出网。见 subagent/handle_request.rs:459-462,505-520。高识别子代理实例；父子链路 HTTP 层不完整。
标题/目标摘要已有材料明确出现 Goal Plan Writer、Goal Summarizer、Goal Strategist system 指纹。见 request-source.js:90-100 与提示词构成报告。中到高：可标为 goal/title 类自动化，但需区分用户可见计划。
压缩默认 85%；专用压缩模型/模板；two-pass prefire；compaction checkpoint 和 compaction request 工件。见 session/compaction.rs:1813-1981、compaction_utils.rs:918-978。高：结构指纹+时序可识别。
plan/reviewGoal Plan Writer、Plan agent、enter_plan_mode/exit_plan_mode 工具；工具集合和 system prompt 变化。中到高。

3.4 OpenCode

类型可观察信号结论
主对话多条 system 或 OpenAI OAuth 的 instructions；正常 SessionPrompt 循环。默认类型。
子代理网络层没有会话/子代理头；parentID 只在本地 session DB；task 子会话仍跑完整循环。见 packages/opencode/src/session/。低：仅 system/消息指纹启发式。
标题源码材料明确存在 summary/title agent prompt 家族，但当前网络端不一定暴露 agent 名。短输入、无工具、输出短是辅助信号。中：须用 system prompt 精确指纹或会话事件关联。
压缩明确端点 POST /session/:id/summarize；自动压缩使用隐藏 compaction agent；压缩时 system:[]，messages 通常只有一条带序列化历史的 user。见 compaction.ts:420-445、processor.ts:477-482。高：端点优先，body 形状次之。
plan/reviewAgent prompt 可替换基础提示词；plan/review 是否独立调用取决于插件与 agent 配置。低到中。

3.5 Qwen Code

类型可观察信号结论
主对话普通 Qwen Code system/environment context；promptId 只有 session 前缀或常规序号。默认类型。
子代理promptId=sessionId#subagentId#promptOrdinal；system 有「general-purpose subagent working for a parent agent」；运行时事件含 subagentId。见子代理报告与 server/utils/attribution.js:96-100 的兼容解析。中到高：可解析复合键，但父关系部分间接。
标题现有源码材料未确认稳定的 title 专用请求；分析类 prompt 可能与自动化摘要混淆。待验证。
压缩全历史压缩，支持可配置 compression model；压缩输入为历史浅拷贝，system instruction 独立传递；失败可反应式 RETRY，结果有 COMPRESSED/NOOP/OUTPUT_TRUNCATED 等状态。见 services/chatCompressionService.ts:430-487、turn.ts:351-381。中到高：body 形状与压缩模型组合。
plan/review压缩后会重建 plan-mode reminder；后台 subagent 快照和 plan reminder 是结构化附件。中。

4. 重点：会话标题生成

4.1 能确认什么，不能确认什么

会话标题是本任务中最容易误判的维护流量。一个客户端可能在首条用户消息后生成一次标题，也可能在首轮完成后异步生成；标题请求还可能由服务端完成，客户端不会向 CrewRouter 发第二个模型请求。现有材料能确认 OpenCode 有 summary/title agent prompt 家族、Grok 有 Goal 系列 prompt 指纹；但对 Claude Code、Codex CLI、Qwen Code、Hermes、OpenClaw、DeepSeek，不能仅凭当前仓库报告断言存在或不存在独立 title 请求。

客户端独立标题请求证据可能辨别方式置信度
Claude Code未确认固定 title API专用 system 指纹、首条 user 后紧跟的短输出请求；否则归 primary/other低
Codex CLI未确认；不要把 review/compact 头当 title专用 x-openai-subagent 值若未来出现，优先按值；无值时用短输出+时序低
Grok BuildGoal Plan Writer/Summarizer/Strategist 指纹可见system prompt 精确匹配；模型/输出较小；首轮或目标状态改变后异步出现中
OpenCodesummary/title agent prompt 家族出现在提示词构成材料agent prompt 指纹；无工具；短 user history/短 completion；关联同一 session 的上一请求中
Qwen Code未确认固定 title 调用专用 system/模型指纹；避免仅凭 max_tokens 小判定低
Hermes未确认；离线摘要器不等于标题器若有 title marker 或短异步请求再建立规则低
OpenClaw未确认独立上游标题调用优先查 Gateway 事件/本地 session entry；HTTP 层没有证据则不强行分类低
DeepSeek未公开只能记录未知自动化请求低

4.2 标题请求的可操作组合规则

  1. 强规则：命中显式 title/summary endpoint、header 或 system prompt 的专用固定短语时，分类为 title，置信度 high。
  2. 中规则：无工具定义、输入主要是首条或短历史 user 内容、输出上限显著小于主对话，且发生在会话首条消息后 0–10 秒内；分类为 title，置信度 medium。
  3. 排除规则：命中 x-openai-subagent=compact、OpenCode /summarize、单条超长历史序列化 user 或 compaction marker 时，优先归 compaction，不要被短 completion 覆盖。
  4. 不确定规则：只有「短输入+短输出」而没有时序、模型或 prompt 证据时，归 other_automation / low，不归 title。
title_candidate = no_tools
  && short_or_first_turn_history
  && completion_cap_small
  && (title_prompt_match || follows_first_user_request)
  && !compaction_signal
  && !subagent_signal

4.3 如何验证标题事实

建议为每家客户端准备干净会话，记录完整的 method/path/headers/body/model/时间戳，并分别测试：首条消息、第二条消息、重命名会话、长对话压缩、离线/断网恢复。将请求按 session/thread 排序，重点观察首条 user 后是否出现「同一 session 的短请求」，以及该请求是否含专用 title prompt。只有重复实验得到稳定序列后，才把规则升级为 high。

5. CrewRouter 网关落地建议

5.1 入库与计费

  1. 保留协议类型和语义类型两列概念。不要用现有 request_type 覆盖语义；协议类型继续表示 chat/anthropic/responses，语义写入 plugin_meta.request_semantics，避免运行时 schema 迁移扩大范围。
  2. 维护性请求单独统计。标题、压缩、缓存预热、后台摘要可标记 is_maintenance=true；默认报表分别展示总 token、业务 token、维护 token。是否收费应由产品策略决定，不要由低置信度分类器自动免单。
  3. 子代理按 thread/session 分账。Codex 用 thread_id，Hermes 用 session/subagent ID，Grok 用子 session ID，Qwen 解析 promptId；Claude Code/OpenCode 无强信号时保留 unknown，不要把 system 指纹当成绝对事实。
  4. 重试去重而不是删账。每次 HTTP 尝试都保留原始记录，并用相邻请求指纹关联 retry_group_id；报表可以同时展示尝试次数和最终业务回合成本。
  5. 记录分类器版本与命中原因。规则会随着客户端版本变化；没有 classifier_version 和 reason_codes，历史报表无法解释分类漂移。

5.3 建议的报表视图

  • 用户回合视图：按 root session/thread 聚合 primary + 子代理 + maintenance，展示总成本和各类占比。
  • 维护开销视图：单独展示 title、compaction、retry、review、other automation 的请求数、输入 token、缓存命中率和失败率。
  • 不确定性视图：按客户端和 classifier version 统计 low/medium/high 比例，帮助决定哪些规则值得继续抓包。
  • 缓存视图：压缩前后 prompt token 突降、缓存命中率突降的时间点，与 compaction 标记联动，解释成本尖峰。

6. 边界、误报与验证方法

不能从 HTTP 层确定的情况：客户端在本地完成标题/摘要、服务端代做标题、子代理复用完全相同的 system prompt、用户消息恰好长且像序列化历史、以及客户端自定义 system prompt。此时应记录 unknown/low，而不是伪造确定分类。
风险典型误报缓解
短请求误报把所有低 max_tokens 请求当 title要求 title prompt 或首轮时序等第二证据。
长 user 误报用户粘贴长日志被判 compaction必须同时满足无工具、历史格式 marker、system 极简；增加序列化字段检测。
子代理误报system 中出现 subagent 字样但其实是用户自定义 prompt专用 header/body 优先；system 指纹只给 medium/low。
重试重复计费429 后相同请求被当两个业务回合保留两条尝试记录，使用 retry_group_id 做报表聚合。
本地压缩漏记OpenClaw/Hermes 压缩发生在客户端，网关只看到下一次普通请求不要声称「没有压缩」；记录不可观测，依赖客户端事件或 prompt 长度突降。

6.1 最终总结

八家客户端的共同事实：一次用户交互不等于一次模型请求。主对话可能派生子代理、计划/评审、压缩和重试；标题请求则不是所有客户端都能从公开源码确认，甚至可能由本地或服务端完成。

标题生成的可辨别方法：优先使用显式 title/summary endpoint 或专用 system prompt；其次组合「首条消息后短时序 + 无工具 + 短历史 + 小输出上限 + 非压缩形状」。仅凭短输入或小模型不能定类。

网关最重要的落地动作：把语义分类作为带证据和置信度的附加元数据；用 Codex/Hermes/OpenClaw 的结构化链路做高置信度父子归因；用 OpenCode endpoint 和 Codex compact header 识别压缩；对 Claude Code、DeepSeek 以及未确认的 title 流量保持诚实的 unknown；在报表中分开业务 token、维护 token 和重试尝试。
