01结论摘要

SuperGrok 额度没有一份官方公开 API 文档。实际可用的查询途径有三条，对应三套完全不同的额度模型：

网页端 · 聊天/请求额度
登录 grok.com 后调用内部接口 POST /rest/rate-limits，返回剩余请求数、限流等待时间。未被官方文档化，属逆向所得。
网页端 · 图像额度
Imagine 图像生成走 /rest/media/imagine/quota_info，返回剩余图像生成次数与重置信息。
Grok Build CLI
本仓库的 /usage 命令通过 x.ai/billing 扩展查询编码信用额度（周度/月度共享用量池），走 cli-chat-proxy 网关。
开发者 API
api.x.ai 控制台展示开发者账号自己的限流，与 SuperGrok 订阅相互独立，不共享额度。
路径额度对象入口认证关键字段
网页端 RESTSuperGrok 订阅的聊天/请求额度 POST https://grok.com/rest/rate-limits 登录 Cookie（非公开，未文档化） remainingQueries、waitTimeSeconds、modelName、requestKind
网页端 Imagine图像生成额度 /rest/media/imagine/quota_info 登录 Cookie（非公开） 剩余生成次数、重置信息
Grok Build CLI编码信用（周度/月度用量池） GET {cli-chat-proxy}/billing?format=credits OAuth Bearer + X-XAI-Token-Auth + x-userid creditUsagePercent、currentPeriod、prepaidBalance、isUnifiedBillingUser
开发者 APIAPI Key 的独立限流 api.x.ai console / REST API Key（官方公开） RPM/TPM、usage 对象

02grok.com 网页端 —— POST /rest/rate-limits

xAI 没有为 SuperGrok 消费者订阅提供公开 API。但网页前端（Next.js 应用 grok.com）自己会调用一个内部 REST 接口来渲染「剩余额度」提示。该接口被多个社区脚本（Tampermonkey 用户脚本、浏览器扩展）通过抓包逆向并复用。以下内容主要依据两个可公开获取的逆向脚本全文：Grok Rate Limit Display（greasyfork 脚本 533963）与 grok-userscripts（GitHub nisc/grok-userscripts）。

⚠ 非官方接口 该接口未在官方文档中公开，随时可能变更或要求额外校验；请求需携带登录态的 Cookie，且可能被风控。任何第三方脚本/工具依赖它都存在失效风险。仅供学习与个人使用。

2.1 请求

POST https://grok.com/rest/rate-limits
Headers: Cookie: …（登录态）; Content-Type: application/json
Body:
{
  "requestKind": "SUPER_GROK" | "STANDARD_GROK" | "TEMPORARY_SUPER_GROK" | …,
  "modelName": "grok-4" | "grok-4-fast" | "grok-code" | "grok-imagine" | …
}
  • requestKind：请求所属的档位/渠道。值为枚举字符串，如 SUPER_GROK（SuperGrok 订阅）、STANDARD_GROK（免费档）、TEMPORARY_SUPER_GROK（临时试用）等。前端从登录用户的订阅信息中取得。
  • modelName：查询哪个模型的额度。不同模型（聊天主模型、Fast 模型、代码模型、图像模型）的额度相互独立，各自有独立的限流桶。
  • 接口还支持批量/分组查询变体，一次请求可携带多个模型的额度请求。

2.2 响应

{
  "remainingQueries": 8,
  "highEffortRateLimits": {
    "remainingQueries": 8,
    "limit": 15,
    "waitTimeSeconds": 0
  },
  "lowEffortRateLimits": {
    "remainingQueries": 50,
    "limit": 60,
    "waitTimeSeconds": 0
  }
}
字段含义
remainingQueries当前模型/档位下剩余可发起的请求数
highEffortRateLimits高努力（深度推理）请求的独立限流桶：remainingQueries 剩余数、limit 窗口内总数、waitTimeSeconds 距重置的等待秒数
lowEffortRateLimits低努力（快速响应）请求的独立限流桶，字段同上
resetAt/waitTimeSeconds部分变体携带重置时间戳或等待秒数，用于前端倒计时

前端拿到 remainingQueries 后在输入框附近显示「剩余 X 次查询」，或用 waitTimeSeconds 显示「X 秒后可继续」。

2.3 已知的 modelName / requestKind 取值（来自逆向脚本）

枚举说明
grok-4 / grok-4-fast / grok-4-mini聊天主模型（慢/快/轻量）
grok-code代码模型（Coding）
grok-imagine图像生成（Imagine）
grok-voice语音会话
SUPER_GROKSuperGrok 订阅档位（含 Plus / Heavy 的请求渠道标识）
STANDARD_GROK免费档
TEMPORARY_SUPER_GROK临时 SuperGrok（试用/赠送）

2.4 图像额度（Imagine）

图像生成的额度单独查询：/rest/media/imagine/quota_info，返回用户剩余的图像生成次数及重置信息。与聊天 remainingQueries 是两套独立额度。

2.5 网页端「设置 → Usage」页面

登录 grok.com 后，设置 → Usage（https://grok.com?_s=usage）会展示当前周度/月度的共享用量池进度。该页面数据同样由前端调用内部接口获取（对普通用户即最终查询入口，无需自己写请求）。

03Grok Build CLI（本仓库）—— /usage 与 billing 链路

本仓库（grok-build）的 CLI 为开发者提供了一个 官方、带认证、有代码佐证 的额度查询路径——但它查的是 Grok Build 编码信用（一个独立的消费额度，与网页端 SuperGrok 聊天额度不是同一个池）。

用户输入 /usage→ ACP 扩展 x.ai/billing→ GET {cli-chat-proxy}/billing?format=credits→ 后端 GetGrokCreditsConfig→ CreditBalance 展示

3.1 调用链与认证

核心实现在 crates/codegen/xai-grok-shell/src/extensions/billing.rs：

GET {base}/billing?format=credits
base = cli-chat-proxy 网关，默认 https://cli-chat-proxy.grok.com/v1

Headers:
  Authorization: Bearer {access_token}
  X-XAI-Token-Auth: {GrokComConfig::default().token_header}
  x-userid: {user_id}
  x-grok-client-version: {VERSION}
  X-Client-Mode: {process_client_mode()}

网关随后转发到后端 GetGrokCreditsConfig。另有 GET {base}/auto-topup-rule（对应 GetAutoTopupRule）查询自动充值规则。

3.2 响应结构（BillingConfigResponse）

源码中的反序列化结构 BillingConfig 同时兼容新旧两种后端返回（GetGrokCreditsConfig 与遗留 GetGrokBuildBillingConfig）：

字段含义
creditUsagePercent已用信用占额度百分比（0–100），首选字段
currentPeriod当前用量周期：type（如 USAGE_PERIOD_TYPE_WEEKLY）、start/end（RFC3339 时间戳）
onDemandCap / onDemandUsed按需（pay-as-you-go）消费上限与已用（美元分值 Cent）
prepaidBalance预购（充值）信用余额，>0 表示已购买的额外额度
isUnifiedBillingUser是否统一用量池（共享周度/月度池），来自远程配置 unified_consumer_billing_enabled
productUsage按产品拆分的用量百分比（如 PRODUCT_GROK_BUILD）——当前 CLI 展示面尚未使用
history历史周期用量（billingCycle、includedUsed、onDemandUsed、totalUsed）
monthlyLimit / used / billingPeriodStart/End遗留字段（旧月度模式），新字段缺失时兜底

金额字段用 {"val": …}（美分）表示；proto3 JSON 会省略 0 值，所以解析时都有 default 兜底。

3.3 订阅档位与额度耗尽处理

  • 档位检查：x.ai/auth/check_subscription 返回的 AuthMeta 里带 subscription_tier；is_max_tier() 将小写化/空格转下划线后的档位与 supergrok_heavy 比对，判断是否为最高档（SuperGrok Heavy）。
  • 耗尽判定：is_credit_limit_error() 识别 402（必为额度/消费阻断）、403 + 正文含 "run out of credits"（遗留文案）、429 里的 "You ran out of credits" 等。
  • 升级/充值弹窗：open_credit_limit_upsell() 依据用量池模式（统一池 → 建议买预购信用；遗留 PAYG → 建议开启/调高按需上限）弹 Q&A 模态框；最高档用户推内联卡片并跳 https://grok.com?_s=usage 管理用量。
  • 自动轮询：用量 ≥ 99% 时开启高频轮询，并在耗尽时自动重查订阅（用户升级后自动重试暂存的 prompt）。

04api.x.ai 开发者 API 对照（相互独立）

如果你有 api.x.ai 开发者账号，那是另一套额度体系，与 SuperGrok 订阅互不相通：

  • 查询入口：api.x.ai 控制台的 Rate Limits 页面展示当前 API Key 的 RPM（每分钟请求数）/TPM（每分钟 Token 数）及用量；数据也可通过 REST 接口获取（官方公开）。
  • 响应中的用量：API 响应体带 usage 对象（prompt_tokens、completion_tokens、total_tokens），用于按请求计量，但不等同于订阅「剩余次数」。
  • 付费：开发者 API 按 token 计费，可在控制台查看余额与消费；SuperGrok 是订阅制（按周/月重置的包含用量 + 可预购信用），两者额度模型不同。
