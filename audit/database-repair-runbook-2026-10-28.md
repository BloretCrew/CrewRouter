# 数据库分阶段修复方案（2026-10-28）

## 状态与边界

本方案依据 `audit/database-integrity-2026-10-28.md` 的只读检查结果，以及 PostgreSQL 18 官方手册中 pg_dump、pg_restore、ALTER TABLE 和连续归档恢复章节编制。本次只编写方案，没有执行备份、恢复、业务写入、服务停机、迁移或权限调整。

目标是恢复可证实的业务事实、防止新增异常，并可审计地处理无法恢复的数据，而不是把异常计数改成零。现有 100 个已声明外键和 41 个序列检查通过，没有依据先重置序列或大规模重建索引。

仓库已有 `audit/security-recovery-runbook-2026-10-25.md` 事件恢复记录。本次没有重新确认主机可信性；不能默认原主机、当前库或同机备份是可信恢复源。来源、时间点、校验信息和恢复环境均应单独核实。

## 1. 确认修复源和操作窗口

先确定：

1. 异常发生前的可信备份、其时间点，以及独立保存的备份清单或日志。2026-10-27 巡检基线自身已有异常，不能因为备份时间接近该日就认为干净。
2. 是否有符合物理恢复要求的基础备份及覆盖所需时间段的连续 WAL。只有逻辑 dump 不能用于 WAL 时间点恢复；现在开启归档也不能补回已丢失的历史 WAL。
3. 恢复后需保留哪些较新的有效业务记录，以及账号、权限、配额、资金和请求保留策略。
4. 在正式改库之前，经业务确认安排暂停写入、计费、后台清理、配额重算和自动迁移的维护窗口，或制定可靠的增量捕获及切换方案。本文件不执行这些操作。

有可信恢复源时，在隔离环境恢复并与当前库比较；没有时，只能从可验证的上游请求记录、审计记录、账本或快照恢复能够确定的字段。不能承诺无来源地重建全部历史事实。

## 2. 保全当前状态，验证回退能力

在独立可信存储中保存当前数据库导出、结构、日志和操作记录。当前导出是回退与取证材料，不代表干净备份；不要覆盖任何更早备份或放入 Git。

下面是待授权执行的导出模板，不会由本次对话自动运行。先由操作者显式设置 SOURCE_PGHOST、SOURCE_PGPORT、SOURCE_PGUSER、SOURCE_PGDATABASE、EVIDENCE_ROOT，并通过权限受限的密码文件提供凭据。使用 PostgreSQL 18 客户端，确认账号可读取全部需要保全的对象；不要把密码放入命令行或输出到日志。

```bash
set -euo pipefail
umask 077
: "${SOURCE_PGHOST:?必须明确源主机}"
: "${SOURCE_PGPORT:?必须明确源端口}"
: "${SOURCE_PGUSER:?必须明确导出角色}"
: "${SOURCE_PGDATABASE:?必须明确源数据库}"
: "${EVIDENCE_ROOT:?必须明确仓库外可信证据目录}"
EVIDENCE_DIR=$(mktemp -d "${EVIDENCE_ROOT}/crewrouter-db-$(date +%Y%m%dT%H%M%S)-XXXXXX")
pg_dump --host="$SOURCE_PGHOST" --port="$SOURCE_PGPORT" \
  --username="$SOURCE_PGUSER" --dbname="$SOURCE_PGDATABASE" \
  --format=custom --file="$EVIDENCE_DIR/current-before-repair.dump" \
  2>"$EVIDENCE_DIR/pg_dump.stderr"
sha256sum "$EVIDENCE_DIR/current-before-repair.dump" > "$EVIDENCE_DIR/SHA256SUMS"
pg_restore --list "$EVIDENCE_DIR/current-before-repair.dump" > "$EVIDENCE_DIR/archive-manifest.txt"
```

pg_dump 的一致性快照用于保全导出开始时的数据，不会自动恢复此前丢失的值；它也不覆盖集群级角色等全部恢复依赖，需另行记录并审查权限与配置。导出成功、目录可列出或自算 SHA-256，都不等于已经证明备份历史可信或可完整恢复；必须在隔离环境做恢复验证。

## 3. 恢复到独立隔离环境，不覆盖生产

- 使用独立可销毁的 PostgreSQL 18 实例，禁止连接生产业务、使用生产运行凭据或访问不必要网络。不要仅凭不同数据库名就认为已经完成安全隔离。
- 对来源不可信的 dump，先审查其生成的 SQL、函数、触发器、扩展和权限内容。pg_restore 可能执行归档内的代码；--no-owner 和 --no-privileges 不能把不可信归档变安全。
- 使用新的空数据库进行恢复，不使用指向生产的 --clean、--create，不通过禁用触发器或 session_replication_role 绕过错误。
- 对已审查的 custom 归档，可在明确指定的隔离空库中使用 --exit-on-error、--single-transaction、--no-owner、--no-privileges；必须检查退出状态、恢复日志及对象完整性。原子恢复并不代表业务内容正确。
- 不自动启动恢复库对应的应用、插件、定时任务或启动迁移；先检查与已审查源码的结构差异，明确每项迁移及种子数据的影响。
- 当前状态副本与可信历史恢复副本分开保存，逐表、逐主键及关键字段对比。恢复旧备份后还需单独合并其时间点之后能够证明有效的数据，不能直接覆盖这些较新记录。

## 4. 逐类修复数据，不编造业务事实

| 问题 | 可接受的修复依据 | 无法证实时的处理 |
| --- | --- | --- |
| 用量时间 NULL、远期或不合理年代 | 可信备份中的原值，或与该记录唯一对应的上游事件时间；核实墙钟、时区及时间单位 | 保留原值与证据，标记待核实并明确统计覆盖范围；不统一填 NOW() |
| 负 Token | 可信备份、原始上游 usage 或可逐请求核对的日志；按模型协议核对缓存及加权口径 | 标记异常，避免作为可信计费依据；不取绝对值、不清零、不直接重算余额 |
| 分析记录缺 usage_id | 可信备份或可证明一对一的稳定请求标识，同时验证用户和请求身份 | 保留待核实或经批准归档；不按行号、相邻 ID、总行数或时间相近强行配对 |
| 请求引用不存在的用量 | 核实历史清理及归档记录；有可信源时补回对应事实 | 对合法保留策略造成的不可追溯显式记录，不创建虚假用量占位记录 |
| 请求缺逻辑请求 | 核实同一稳定逻辑请求标识及其审计记录，必要时从可信源回补 | 标记缺口并追查异步落库，不凭请求数量生成成功历史 |

ID 曾被重置或复用时，仅主键相同不足以证明两条记录是同一业务事实。回补前同时核对稳定请求标识、用户、供应商、模型及来源时间点等可用信息；冲突必须单列，不能自动覆盖。

配额区间记录保留 snapshot 是现有设计。不能把所有找不到原始 attempt 的区间记录直接删除，也不能给每个 _id 字段盲目加外键。

每批修复均需保存原值、来源、批准依据、更新前提和结果。使用小事务及乐观校验：只有生产现值仍等于审核时旧值才更新，实际影响行数必须符合批准清单；不匹配即停止。涉及余额、兑换记录或费用追补需独立业务审核，不能按残缺用量自动补账或退款。

无法证实的记录不进入伪造的“已修复”集合。若业务决定将其从活跃表移出，应先保全并设计所有依赖、保留统计和回退方案，再单独批准；本方案不授权删数据。

## 5. 修正写入入口，再逐步收紧结构

在独立测试数据库中修复并验证以下写入契约：

- 普通请求、流式请求、Playground、Agent、模型探测等用量写入都经过相同的 Token 合法性及字段完整性校验；明确未知值与非法负值的区别，检查整数范围和时间单位转换，避免静默转换或钳制掩盖上游问题。
- 服务端生成记录时间，按既定时区语义保存；不得对整库重复做 UTC/上海时间平移。新记录的未来时间容差和历史导入规则应明确区分。
- usage 与消息分析以真实记录 ID 关联；逻辑请求与请求尝试要有明确的失败补偿或持久化重试机制，不能只有忽略失败的异步写入。
- 新数据先满足契约，再迁移约束。历史必填值完成恢复或获批处理后，补回与源码一致的 NOT NULL；对确定适用的 Token 字段增加非负校验，对符合保留策略的业务关联决定是否新增外键。
- 分阶段使用 NOT VALID 与 VALIDATE CONSTRAINT 时，注意 NOT VALID 仍会约束之后的 INSERT/UPDATE，可能使对旧坏行的无关字段更新失败；必须先做应用兼容测试，并控制锁等待及维护窗口。
- 不依赖 CREATE TABLE IF NOT EXISTS 修复既有字段定义，不为了顺利导入而删除约束或禁用触发器。

相关代码入口包括 server/routes/api.js、server/routes/playground.js、server/utils/agent-billing.js、server/utils/message-analysis-store.js、server/utils/request-quota-capture.js、server/utils/quota-request-context.js，以及 server/index.js 的建表与迁移逻辑。修复前应继续定位具体异常来源，不能预设所有异常都由应用写入造成。

## 6. 验收与切换

验收至少包含：

1. 与可信恢复源的表、主键集合、关键字段和权限对账；对保留策略、增量合并或重算造成的差异逐项说明。
2. NULL、未来日期、负 Token 和关联缺口均已恢复，或有经批准、可追踪的未解决记录清单；不能只靠删除异常令计数归零。
3. 重跑全部已声明外键、适用业务关联、序列、约束验证及关键业务查询。
4. 在隔离库验证正常、流式、中断、重试、并发、异常上游 usage、计费和回滚流程，不使用生产 config.json 或端口进行回归。
5. 资金及 Token 汇总按可信账本与可验证原始记录核对，保留未覆盖范围，不把错误记录数量或行数相同视为业务完全恢复。
6. 在维护窗口内按批准计划应用，保存切换前状态及最后增量；业务验收后再恢复必要任务。

当前 30 个 API Key 的禁用状态单独核实，不随数据修复统一启用。涉及历史事件的凭据与管理员身份需独立验证或轮换；不能把旧备份里的可用凭据恢复当作完成恢复验收。

建议立即确定的输入是：异常出现前的可信备份路径或备份时间点；如无备份，则提供可用于逐请求核实的原始日志、上游记录或账本来源。在这些输入明确之前，先做证据保全和隔离验证，不执行不可逆清理。
