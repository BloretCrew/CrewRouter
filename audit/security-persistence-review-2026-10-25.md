# 持久化、审批和授权撤回专项复核（2026-10-25）

本轮继续检查可能造成数据库数据错乱的应用写入。以下缺陷均通过真实路由/函数、合成数据与全新私有 Unix socket PostgreSQL 复现；没有据此认定攻击者实际利用过这些路径，也没有自动修复生产历史数据。

## 对话替换失败会丢失原历史

旧替换接口先独立删除历史，再逐条插入新消息。原历史为 `original` 时，提交一条合法 `partial` 及一条缺少 content 的消息，响应 500 后只剩 `partial`。创建、追加和 fork 也可能部分成功。

现在先完整验证和序列化消息批次，再以同一连接、同一事务完成写入。替换、追加和删除消息先锁所属用户的父对话，读取及 fork 共享锁住父对话，避免并发生成混合历史或复制不同版本。fork 按原消息 ID 顺序复制，失败不留空副本。不存在和不属于当前用户的对话统一返回 404。

当前两个客户端持久化的消息内容是文本，数据库列也是 TEXT；新增验证按此接受字符串，非法消息、NUL、无效 UTF-16 和无法写入的 JSON 在修改历史前返回 400。显式空数组仍可清空历史。这不能恢复旧代码已经删除的消息。

## 插件授权撤回会被并发覆盖

旧接口对全局 `settings.plugin_pref_optin.users` 读后改写。合成初始授权 `[7]`；用户 8 读取后暂停，用户 7 撤回成功，再恢复用户 8，最终却得到 `[7,8]`，恢复了已撤回的授权。

现在在短事务中确保设置行存在，再对同一行 `FOR UPDATE`，锁内读取、修改并提交。首次创建行及授权/撤回两个方向的交错均受保护，响应在提交后发送。旧授权来源和历史撤回情况仍须结合可信记录核验。

## 通知规则的事务使用了不同连接

旧通知规则替换使用 `pool.query('BEGIN')`，后续删除、插入与回滚并不保证落在同一连接。用两个真实连接轮转复现连接池的合法调度：BEGIN 在 A，DELETE 在 B 自动提交，插入失败后 ROLLBACK 不能恢复原规则，接口返回 500 而原规则已为空。

现在从连接池借出单一 client 完成整笔事务，并先锁用户行，使初始无规则时的并发替换也能串行。故障完整回滚；用户已不存在返回 404，不遗留事务。选择项去重，空选择仍保留原通配符语义，其他用户的规则不受影响。

## 供应商同步可能清掉绑定却没有禁用模型

旧同步逐条独立提交。注入最终禁用模型失败，响应 500，但 Team、Key、Harness 映射已删除，Key 的当前模型已清空，模型本身仍处于启用状态。

现在先在事务外获取并验证上游模型列表，之后用短事务锁供应商，并核对取列表前后的相关配置。模型新增、启用、禁用及 Team、Key、Harness、Fusion 关联清理与自动授权全部使用同一 client，失败完整回滚。提交后才清理本进程缓存；缓存清理失败不会把已提交同步误报为未执行。

`addOnly` 和原有成功响应字段保留。无效列表不写库，已从上游列表消失的选择返回 409，供应商相关配置中途变化也返回 409；既有重复上游映射拒绝执行，不任意选择一条。该行为要求客户端刷新列表后重试。上游仅用合成响应验证，没有调用真实供应商。

## Agent 历史、计费及审批的一致性

确认了三个独立问题：

- 用量先单独落库，扣款返回 `{ok:false}` 却被忽略，余额不足仍能记入费用并返回成功。
- 两次并发替换同一线程消息，均从旧历史出发，最后可能混入两份生成结果；仅给最后保存阶段加锁不足以防止旧快照覆盖。
- 工具操作、审批终态、工具结果消息和审计分散执行。工具成功后审计失败会返回 500，审批仍 pending；重复请求可再次执行工具。

现在每个管理 run/approval 从读取历史到后续处理结束，使用跨进程的线程 advisory try-lock；同线程竞争返回 409。锁使用独立 `pg.Client`，不占主连接池槽位，网络等待期间不开事务，支持主池 `max=1`。管理写入的短事务直接复用该连接；如果 session 丢失，锁虽被释放，旧 run 也无法另借主池继续提交。所有退出路径最终解锁并关闭连接。

审批短事务按线程、审批、当前管理员身份及工具目标的顺序锁定，重查 pending；工具修改、审批终态和工具结果消息一起提交。提交后审计失败不会恢复 pending 或反转成功状态。提交后读取历史失败返回受控 503，明确包含 `approval_applied:true` 和审批终态；重试不能再次消费。后续生成的 `run.failed` 表示续答失败，已批准工具操作和结果消息保留。

计费先锁用户，在锁内、插入本次用量之前决定 quota 和实扣积分，保留原 Agent 的免费额度边界；必须检查扣款结果。扣款、用量、管理历史/新审批，或图片持久化在同一短事务提交，任一步失败全部回滚。`run.completed` / `approval.required` 在提交后发送，提交后的用量关联采集失败仅记录错误。线程读取使用短 `REPEATABLE READ READ ONLY` 事务，使线程、消息与 pending 审批来自同一快照。

外部模型已经执行的生成无法通过数据库回滚撤销费用；连接失效或最终扣费失败仍可能发生上游成本。本补丁没有预留所有外部调用额度，也没有声称消除这类损失。已批准的工具操作与后续生成是两个提交阶段：续答失败不会撤销已批准操作。
