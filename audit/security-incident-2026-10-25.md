审计日期：2026-10-25  
范围：用户提供的两份复盘材料、CrewRouter 应用代码、此前完成的数据库只读审计与处置记录。  
证据限制：复盘材料提及的 `/root/INFRA-ARCHIVE-20261023/` 与 `/root/ATTACKER-ARTIFACTS-20261023/` 在当前主机不可用。另有 `/root/attacker-residue-20261023-113349.tar.gz`，本轮仅在归档内只读检查，未解压或执行。该包来自受影响主机，归档内容与成员时间戳都没有独立可信来源，不能替代原始磁盘镜像或异机日志。

## 结论

复盘材料记载，2026-10-18 至 10-21 攻击者在 jinan、bloret-core、detrital-server、bloret-oat、detrital-cloud（0.7）和 bloret-win 六台主机活动；10-22 发现服务异常并确认其他业务数据库及备份被删除。材料将最初入口归因于 jinan 公网 MCSManager 守护进程 `34685` 的权限绕过，并描述了凭据复用、Tailscale、浏览器密码库和管理面板构成的横向移动路径。该跨主机攻击链与命令总数来自所提供的复盘材料；本次没有原始主机镜像或原始命令记录可在工作区独立复核。

CrewRouter 数据库位于另一块盘，未随 `/opt` 删除，但应用数据受到攻击且存在错乱。CrewRouter 自身日志和数据库审计记录显示，应用记录的来源 IP `38.76.194.61` 于 10-18 通过密码和 2FA 成功登录；随后约三小时内记有 42 次供应商创建成功和 6 次删除成功。相关操作日志的操作者用户名均为管理员账号 `Detrital`，但这只能确认应用记录使用了该账号，不能识别实际操作者。登录日志把该管理员的 `is_admin` 记成了 false；供应商创建记录缺少资源 ID，且一个供应商删除 ID 出现两次成功记录，因此这些行数不能直接视为不同供应商的增删数量。审计记录包含 `artex-diag-105`、`artex-i143` 与 SSRF 探测配置，另有两条 `artex-i121` 创建记录来自 loopback。集群复盘材料将相关样本写作 `artex-diag-1051`、`artex-i1431`；由于标识末尾存在差异，不能在缺少原始取证包时断言它们与审计记录是同一条记录。应用 IP 字段也不是独立网络流量证据；由于运行版本的代理信任配置存在问题，`38.76.194.61` 应视为日志记录的来源地址，而非独立确认的操作者地址。现库中没有已知恶意供应商，但事件前后数据库基线不完整，不能据此证明所有历史数据均已恢复。

已确认的 CrewRouter 代码根因是 `vm` 脚本沙箱把宿主对象传入隔离上下文，使攻击者可沿构造器链访问宿主 `process` 并执行命令。已加固该沙箱，并修复若干登录、审计和初始化竞态问题。随后还发现已校验的出站 URL 默认跟随重定向，可能绕过 SSRF 校验；本轮已在相关请求上禁止自动跟随，并补充了遗漏的 URL 校验。

继续检查固定出站路径时发现，头像上传过去通过明文 HTTP 将用户选择的图片发往 `img.bloret.net`，并且没有限制图床响应体大小。网络中间人可读取或篡改上传与响应；如果图床持续返回数据，认证用户也可能触发服务端内存增长。代码现改用 HTTPS、将连接固定到 URL 校验时解析的地址、限制单文件和响应体大小、设置 10 秒总请求超时，并拒绝图床返回的跨源头像地址。图片仍会按功能设计发送给图床；这项修复只在工作区，旧运行进程仍未加载。

本轮静态审查又发现 Bark 通知地址可由普通登录用户设置，原代码允许服务端向私网发请求并跟随 Axios 重定向。现已对保存与发送阶段都加入目标地址校验、要求公网目标使用 HTTPS，并关闭重定向；私有 Bark/CPA 服务仅允许通过精确的 `CR_BARK_PRIVATE_ORIGINS` / `CR_CPA_PRIVATE_ORIGINS` 配置放行协议、主机和端口。CPA 与 Bark 均把直连 socket 固定到校验时解析出的 DNS 地址，HTTP Host 与 TLS 仍使用原始主机名；请求不经过环境代理。后续静态审查把 DNS 固定扩展到已校验的供应商、额度、插件、商店、代理订阅和更新请求，并覆盖配置代理时的隧道目标。改动只在仓库，当前运行进程仍未加载；代理服务器自身的地址解析与授权仍需运维单独限制。

新增的遗留归档证据显示，受影响主机上曾生成浏览器数据采集结果，并出现对 Docker 网段的端口探测回显。两个结果文件各包含两个 256 字符、高熵的 `token` 字段候选；这些值没有写入报告。相同文件未包含筛选命中的 Cookie、已保存登录项或浏览历史记录。脚本静态检查未发现网络调用，现有材料不能证明这些令牌或其他数据已被传出主机；考虑到主机已失陷，仍应将浏览器保存的凭据和令牌按暴露处理。

1. **主机和数据库服务器均不能视为可信。** `detrital-server` 与其数据库目标 `bloret-core` 都被复盘列为失陷资产，且已有来自失陷 Tailscale 节点的 root 登录证据。应先取证，再以可信镜像重建这两台主机和数据库服务，从离线可信备份恢复；当前活库的一致性查询无法证明底层数据未被 root 篡改。
2. **凭据轮换仍需完成。** 需要轮换管理员密码与 TOTP、数据库密码、会话签名密钥、供应商 API Key、SMTP/飞书凭据、PassPort 密钥、主机 SSH/Tailscale/MCSManager 凭据，以及任何曾保存在被入侵主机浏览器中的密码。供应商密钥加密主密钥已暴露；换主密钥时须迁移现存密文并与部署同步。部分第三方凭据必须在相应服务控制台撤销，当前仓库审计无法代替该操作。
3. **SSH 特权访问仍需清理。** root 密码登录仍启用；现有密钥没有可信基线，暂时不能安全区分合法和攻击者密钥。事件窗口内已记录来自三台失陷节点的 root 成功认证。应通过可信管理设备确认并重建 authorized_keys，再关闭 root 密码认证。当前 guard 已切断复盘列出的五台其他失陷 Tailscale 节点到此主机的入站流量。
4. **插件 VM 不是安全边界。** `server/plugins/host.js` 的 VM realm 含有宿主函数和内建对象；设置 `CR_TRUST_IN_PROCESS_PLUGINS=1` 后，后端插件应视为主进程代码。当前代码默认拒绝加载后端插件，但 root 服务进程早于该提交启动，不能将该保护视为已在生产生效。13:27 的只读快照显示当前 12 条插件记录全部禁用，磁盘上有 12 个对应目录、其中 5 个含 `main.js`；这不能证明攻击窗口或 PID 1407 启动时的状态，也不能验证磁盘文件来源。插件管理/安装路由要求管理员权限。只读查询在攻击窗口未发现 `plugin.install` / `plugin.uninstall` 日志，但数据库日志异步且不可信。13:30 已为工作区中的安装、卸载、启停、重载、配置更新、重置错误计数和插件数据删除加入审计写入，并等待写入尝试完成；该补丁尚未部署，且日志仍位于同一数据库。长期方案是独立低权限进程/容器隔离并重新设计 API 数据边界。
5. **出站网络策略仍需运维侧收口。** 已校验的动态目标会在直连或配置代理的隧道中固定到本次解析地址，并对自动重定向重新校验；代理服务器自身仍是管理员配置的信任目标，其解析、权限与出口不由该校验覆盖。静态复核新增了对 IPv6 旧站点本地 `fec0::/10` 的拦截，但它尚未加载到当前进程。Bark/CPA 私有允许列表需精确到 origin，不支持通配符、路径或网段，配置本身代表信任目标。出站网络层仍应阻断应用访问未授权内网网段和云元数据。
6. **日志和主机监控尚未提供独立证据。** 本轮启用的 `auditd` 规则只改善后续本机采集，不能恢复历史事件，也不能抵御 root 删除本机日志；PCAP 从 10-24 才开始且留在本机。应在干净系统上把认证、命令执行、进程树、出站连接、监听端口、授权文件和关键目录变更异机留存；以可信基线记录每日差异，并对 web 服务派生 shell、陌生 SSH 登录、隧道进程及非预期出站连接设置确定性告警。
7. **全局数据库授权仍可收紧。** `crewrouter` 虽不具备高危数据库角色属性，但可在 `public` 建对象。应评估撤销 schema CREATE 权限并为应用迁移使用单独的受控角色。
8. **密钥刷新脚本可外传解密后的凭据。** `server/key-refresher.js` 把 `currentKey` 提供给数据库中的脚本，并允许脚本通过受控 fetch 访问任意经 SSRF 检查的公网 URL。SSRF 校验阻止私网目标，但不会阻止把密钥发到攻击者公网主机；若数据库被篡改，脚本可在刷新时窃取供应商密钥。代码现默认拒绝启动、定时、惰性及手动执行脚本；只有进程启动时显式配置 `CR_ENABLE_KEY_SCRIPTS=1` 才启用。该改动尚未加载到当前运行进程，只能在可信重建后的部署中生效。恢复时应逐个审阅脚本和目标域名后再启用，并轮换相关凭据。
9. **自动更新与插件商店制品没有独立签名校验。** `server/utils/updater.js` 限制 HTTPS、关闭重定向并校验 ZIP 结构，但未核验发布者数字签名或可信 SHA-256 清单；插件商店只在 package metadata 提供 SHA-256 时才校验，仍依赖同一 HTTPS 商店源的完整性。管理员触发更新或插件安装时，若发布源/凭据失陷，可把攻击者代码写入服务目录；后端插件还会在显式信任时进入主进程。可信重建前不要从旧主机执行自动更新或安装插件，后续应增加离线/独立签名校验并审查插件源码。
10. **脚本沙箱仍与主进程共享内存上限。** `vm` 超时能限制运行时间，但没有堆内存隔离；恶意或被篡改的额度/密钥脚本可能通过大量分配造成 Node 进程 OOM。VM 逃逸修复降低了命令执行风险，但不能作为资源隔离边界；长期应将此类脚本放入有内存限制的独立 Worker/进程。
11. **自定义额度配置可向公网外传供应商密钥。** 通用额度查询会把数据库中的请求 URL 和请求头与 `{apiKey}` 插值后发出；SSRF 校验只拦截私网目标，不能阻止攻击者公网域名。代码现默认拒绝带有自定义 `quota_script` 的查询，仅在进程启动时设置 `CR_ENABLE_CUSTOM_QUOTA_SCRIPTS=1` 才启用；内置额度查询不受影响。该改动尚未加载到当前运行进程，只能在可信重建后的部署中生效。
12. **主机仍未完成网络隔离。** incident guard 阻断已知五台失陷 Tailnet 节点；在 `tailscale0` 上，TCP `22/111/5901/6080/9090/20003/28888/40020` 与 UDP `111` 仅允许当前管理设备 `.109.60.58`，其他 Tailnet 对端被丢弃。非 Tailnet 接口上的 TCP `22/111/5901/6080/9090/40020`、UDP `111` 以及 TCP `20003/28888` 由本机规则阻断；`.2:5432` 仅允许本机主动连接的已建立回包。Nginx `80`、其他未列端口和主机出站流量不受该 guard 限制；INPUT 基础策略为 ACCEPT，上游 IPv6/云防火墙状态未知。整台主机已失陷，仍需核验上游边界并从可信环境重建。
13. **历史管理员退款仍须与付款凭证对账。** 旧退款接口的汇总/明细不一致及前端成功响应错配可能造成余额回弹或重复人工退款。当前只读快照中退款汇总/明细一致、退款余额为零，`admin.user_refund` 日志也为零条；但日志异步写入，缺少记录不能证明未发生操作，数据库本身也不可信。仍须逐笔核对外部付款凭证和账本变化；不要仅凭当前汇总或页面提示判断是否付款，也不要自动重建历史明细。
14. **CrewRouter 服务没有 systemd 权限收敛。** 当前单元以 root 运行，未启用 `NoNewPrivileges`、文件系统保护、私有 `/tmp` 或网络地址限制，Capabilities 保持默认完整集合。与已确认的脚本沙箱逃逸根因叠加时，应用 RCE 可直接获得主机 root 权限。不要在仍受影响的旧主机上将临时单元修改当作可信恢复；新环境应使用专用低权限账号和经过验证的 systemd 沙箱配置。
15. **存在未由可信基线核验的 root 用户级 Hermes 网关。** `hermes-gateway.service` enabled/active，使用 `/usr/local/lib/hermes-agent` 下的 Python 程序并启动 Node sidecar；sidecar 目前只监听 loopback `127.0.0.1:8789`。unit 文件时间戳早于已知攻击窗口，但时间戳和本机文件均可能被修改。没有证据可据此认定它是恶意程序；在可信重建前应由系统所有者核实安装来源、用途、凭据和出站目标，不要把该 unit 或其状态视为可信。
