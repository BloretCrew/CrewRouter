# CrewRouter 入侵与恢复审计

审计日期：2026-10-25  
范围：用户提供的两份复盘材料、CrewRouter 应用代码、此前完成的数据库只读审计与处置记录。  
证据限制：当前工作区未包含复盘材料提及的 `/root/INFRA-ARCHIVE-20261023/` 与攻击者原始取证包，本文不把复盘中的推断当成独立复核结果。

## 结论

复盘材料记载，2026-10-18 至 10-21 有攻击者在六台主机上活动，10-22 发现服务异常并确认其他业务数据库及备份被删除。材料将最初入口归因于公网可达、以 root 运行且存在认证绕过问题的 MCSManager 守护进程，并描述了通过 Tailscale、浏览器密码库和管理面板横向移动的路径。该跨主机攻击链来自所提供的复盘材料；本次没有原始主机镜像或原始命令记录可在工作区独立复核。

CrewRouter 数据库位于另一块盘，未随 `/opt` 删除，但应用数据受到攻击且存在错乱。CrewRouter 自身日志和数据库审计记录显示，来源 IP `38.76.194.61` 在 10-18 通过密码和 2FA 成功登录后，在约三小时内新增 42 条供应商、删除 6 条供应商；其中包含 `artex-diag-105`、`artex-i143` 与 SSRF 探测配置。另有两条 `artex-i121` 创建记录来自 loopback。现库中没有这些恶意供应商，但事件前后数据库基线不完整，不能据此证明所有历史数据均已恢复。

已确认的 CrewRouter 代码根因是 `vm` 脚本沙箱把宿主对象传入隔离上下文，使攻击者可沿构造器链访问宿主 `process` 并执行命令。已加固该沙箱，并修复若干登录、审计和初始化竞态问题。随后还发现已校验的出站 URL 默认跟随重定向，可能绕过 SSRF 校验；本轮已在相关请求上禁止自动跟随，并补充了遗漏的 URL 校验。

## 数据库与账户处置

- 只读审计发现 41 条自增序列中 15 条小于现有主键。已逐表短锁并校正；复查后没有序列落后。
- 修复了用户 `id=27` 缺失的成员映射，仅加入唯一匹配的既有个人 Team `id=17`。复查未发现团队关联不一致、孤儿映射或未分配用户。
- 清理了事件后仍存的 67 条会话，包含 65 条未过期会话和 26 条管理员会话，要求所有用户重新认证。
- 禁用了库中 30 条启用的用户 API Key；复查启用数为零。使用这些 Key 的集成须轮换并重新签发。
- 当前数据库有 29 条启用供应商记录；未发现已知恶意供应商、脚本 Key 模式或自定义额度脚本。
- 只读查询插件表发现 12 条示例/主题插件记录，当前均为禁用状态；未见启用的插件。
- 复查通过的项目：100 条外键均已验证、无无效索引、无重复用户名或邮箱、无负余额、退款明细一致。
- 数据库角色 `crewrouter` 不是超级用户，没有建角色、建库、复制或绕过 RLS 权限；但仍可在 `public` schema 创建对象。
- 现库约 296 MB。由于缺少可信的恢复前后快照和可比对的事件前基线，无法证明它与报告所述旧库规模或历史行数完整一致。
- 10-15 起的 `teams_name_key` 冲突早于本次入侵窗口；根因是启动迁移对已有团队归属的用户重复创建个人 Team，不应作为攻击证据。

## 已实施的代码修复

- `server/utils/sandbox.js`：不再向脚本 VM 注入宿主对象，限制字符串与 WASM 代码生成，以 JSON 边界传递上下文；结果读取、日志和异步任务均在有时限的 VM 内执行。密钥刷新脚本的 `fetch` 由宿主 broker 代发，仅返回受限 JSON 数据。
- `server/routes/auth.js`、`server/routes/two-factor.js`：登录 2FA 绑定密码验证后的短时服务端会话；旧验证端点要求已登录且仅允许验证本人。
- `server/middleware/csrf.js`：只有不依赖浏览器用户会话的 API Key 请求才豁免 CSRF 校验。
- `server/routes/setup.js`：OOBE 创建管理员时在取得事务锁后重新检查初始化状态。
- `server/index.js`：启动迁移只为没有团队归属的用户补建个人 Team。
- `server/utils/audit-log.js`、`server/routes/admin.js`：审计中间件可从响应提取资源 ID；供应商创建与更新分别记账。
- 出站 URL：供应商额度查询、模型查询与连通性检测、插件 fetch/webhook、代理订阅、插件商店包下载、PassPort 验证等请求不再自动跟随重定向；供应商导入与探测路径补充 URL 校验。重定向会作为未成功的响应处理，需在配置中直接填写最终 URL。
- 新增只读安全审计脚本及默认 dry-run 的数据库序列修复脚本；数据库处置已在本轮之前执行并复查。

## 尚未关闭的风险与后续动作

1. **主机是否已清洁尚未独立确认。** 复盘报告称多台主机获得 root；应用代码和数据库修复不能证明操作系统、SSH 信任关系、systemd、计划任务、浏览器凭据及隧道后门已清理。应以可信镜像重建受影响主机，并从干净设备重置凭据。
2. **凭据轮换仍需完成。** 需要轮换管理员密码与 TOTP、数据库密码、会话签名密钥、供应商 API Key、SMTP/飞书凭据、PassPort 密钥、主机 SSH/Tailscale/MCSManager 凭据，以及任何曾保存在被入侵主机浏览器中的密码。供应商密钥加密主密钥已暴露；换主密钥时须迁移现存密文并与部署同步。部分第三方凭据必须在相应服务控制台撤销，当前仓库审计无法代替该操作。
3. **插件 VM 不是可靠的安全边界。** `server/plugins/host.js` 仍向插件传入宿主函数（包括 `ctx.log`、`ctx.on` 等），并把宿主内建对象放入插件上下文；VM 未禁止字符串代码生成。具备执行插件代码的主体可能从宿主函数构造器逃逸。部署前应把已安装插件视为宿主级可信代码，停用来源不明的插件；长期方案是独立低权限进程/容器隔离并重新设计 API 数据边界。
4. **ZIP 解压还需加固。** `server/plugins/zip.js` 检查了条目路径并限制条目数，但尚未在解压前拒绝符号链接或限制解压后总大小；需补充对符号链接、特殊文件、ZIP bomb 和重复路径的检查。
5. **SSRF 仍受 DNS rebinding 限制。** 当前校验解析域名并检查返回的 IP，但连接时仍按域名解析，无法消除校验与连接间的 DNS 变化。出站网络层仍应阻断到云元数据和内网网段的访问。
6. **日志和主机监控尚未提供独立证据。** 应把认证、命令执行、进程树、出站连接、监听端口、授权文件和关键目录变更日志异机留存；以可信基线记录每日差异，并对 web 服务派生 shell、陌生 SSH 登录、隧道进程及非预期出站连接设置确定性告警。
7. **全局数据库授权仍可收紧。** `crewrouter` 虽不具备高危数据库角色属性，但可在 `public` 建对象。应评估撤销 schema CREATE 权限并为应用迁移使用单独的受控角色。
