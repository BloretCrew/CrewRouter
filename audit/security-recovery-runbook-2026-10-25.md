# CrewRouter 事件后的可信重建清单

日期：2026-10-25

本清单基于 `security-incident-2026-10-25.md` 与用户提供的两份复盘材料。目标是建立新的可信运行环境；它不把现有主机、活数据库或本机备份当成可信恢复源。

## 当前状态与边界

- 复盘列出六台受影响主机：`jinan`、`bloret-core`、`detrital-server`、`bloret-oat`、`detrital-cloud`（0.7）和 `bloret-win`。凡仍承载业务的主机都应纳入重建范围。
- 当前工作区位于 `detrital-server`；CrewRouter 以 root 运行，现有服务进程早于代码补丁启动。
- 2026-10-25 10:15 CST 复核时，CrewRouter 监听 `*:20003`，仍运行旧源码和依赖；Tailnet ping 可达 `bloret-core`，但 TCP `5432` 与 `pg_isready` 均无响应。当前进程的 `proxy-addr` 仍为 2.0.7，旧代码固定信任一跳代理，公网直连时可能伪造客户端 IP。
- 2026-10-25 10:22 CST 再核验：服务仍以 root 运行 PID 1407，监听 `*:20003`；`bloret-core` 可 ping，但 PostgreSQL TCP/`pg_isready` 无响应。当前进程没有 `CR_TRUST_PROXY`，且本机 INPUT 默认策略为 ACCEPT；上游防火墙是否保护应用端口未知。当前仓库生产依赖审计为 0 项，但运行服务仍是旧进程。
- PostgreSQL 目标 `bloret-core`（Tailscale `100.64.0.2:5432`）也被复盘列为失陷资产。2026-10-25 09:30–09:52 tailnet 主机在线且 ping 成功，但 TCP 5432 无响应；CrewRouter 持续连接超时，新的只读审计无法连接。尚不能区分 PostgreSQL 停止与远端防火墙丢包，活库一致性查询也不能证明操作系统或数据库完整。
- 当前主机的 `cr-incident-guard.service` 已阻断已知失陷 Tailscale 节点访问，并限制若干管理端口；它没有封锁公网 CrewRouter/API 端口，也没有隔离数据库出站连接。
- 本轮已在当前主机启用 `audit/cr-incident-audit.rules` 中的执行与关键文件变更规则，并移除了原有 `-a task,never` 抑制项；审计日志仍只在本机，不能作为独立证据，也不能回补历史命令。
- 截至本次审计，指定路径只找到 2026-08-29 的 API Key SQL 文件，没有找到可证明事件前后完整性的 CrewRouter 全库备份。先确认外部/离线备份，再决定恢复或数据抢救路径。

## 按顺序执行

### 1. 保存证据并确定处置窗口

- 由可信管理设备记录当前时间、主机名、网卡/IP、服务进程、监听端口、登录状态、systemd 单元、定时任务和关键授权文件指纹。
- 在隔离存储中保存主机磁盘/虚拟机快照、数据库磁盘快照、现有系统日志及 PCAP；计算 SHA-256 并将哈希与采集人、时间、来源写入异机记录。不要把证据唯一副本留在受影响主机。
- 若需要保全易失证据，先由取证人员采集内存和连接状态，再关停或隔离。不要在原系统上清理后门、升级软件或重装，以免覆盖证据。
- 将本机当前 PCAP 的起始时间记为 10-24；它不覆盖 10-18 至 10-21 的攻击窗口。

### 2. 建立网络隔离

- 在云安全组、路由器或虚拟化网络层隔离六台受影响资产，禁止其与新环境、管理平面和互联网互通；保留单独、受控的取证通道。
- 当前应用入口仍在公网监听。先在上游防火墙限制 CrewRouter/API 与图床端口到可信管理源，或安排维护窗口切流；不要依赖运行在已失陷主机上的进程实施最终隔离。
- 不把 `bloret-core`（`.2`）用作新的日志接收端、备份端或可信跳板。日志和备份目标应位于独立、全新且权限单向的系统。

### 3. 从可信设备轮换凭据

从未登录过受影响主机的管理设备操作，撤销旧凭据后再发放新凭据：

- 云平台主账号、Access Key、DNS/CDN/证书管理令牌及云厂商会话。
- Tailscale 管理员、节点密钥、设备会话和 ACL；移除受影响节点后重新注册干净节点。
- 所有主机的 root/管理员密码、SSH 公钥、SSH 私钥和 MCSManager 凭据。现有 `authorized_keys` 无可信基线，不要直接复制到新机。
- CrewRouter 管理员密码与 TOTP、数据库密码、会话签名密钥、用户 API Key、供应商 API Key、SMTP/飞书、PassPort 和其他第三方密钥。
- 任何曾保存在受影响主机浏览器或浏览器密码库中的密码、Cookie、恢复码和令牌；统一按已泄露处理并撤销旧会话。

轮换数据库加密主密钥时，先在离线副本上验证密文迁移，再把新密钥写入新部署的秘密管理位置；不要将明文密钥写入 Git、工单或临时脚本。

### 4. 重建主机与网络基线

- 从厂商签名镜像或已验证安装介质重装受影响的 Linux 与 Windows 主机；不要以旧根盘、旧系统盘快照直接回滚上线。
- 更新系统与软件后再开放网络。默认拒绝入站，仅开放清单中确需的端口；MCSManager 不再公网暴露。
- 若使用反向代理，将 `CR_TRUST_PROXY` 设为可信代理 IP/CIDR，并在网络层禁止客户端绕过代理直连应用端口；不要只依赖固定代理跳数。
- 禁用 SSH root 密码登录；通过可信设备核准唯一管理密钥，使用独立普通账号与受控提权。
- CrewRouter 以专用低权限服务用户运行；数据库只允许应用专用网络访问。迁移任务使用单独的受控角色，应用角色不应能在 `public` 任意创建对象。
- 初始恢复时停用所有数据库脚本型 API Key；人工审阅每份密钥刷新脚本及其公网请求目标后才逐个启用，并轮换被脚本接触过的凭据。
- 自动更新包必须在隔离构建/发布链路中验证独立签名或可信 SHA-256；当前 updater 只依赖 HTTPS 与 ZIP 结构校验。
- 先部署日志、认证、进程执行和出站连接的异机留存，再接入业务流量。收集端不可由被监控主机删除或改写。
- 为执行审计预留足够本地轮转空间；当前主机配置为每份 64 MiB、保留 14 份。日志可能包含命令参数，不得将原始日志直接发送到 LLM 或其他外部服务。

### 5. 决定数据库恢复来源

按以下优先级选择来源，并保留来源证明：

1. 查找事件前离线逻辑备份或具备可验证时间点的数据库快照；检查哈希、备份任务日志、PostgreSQL 版本和恢复演练记录。
2. 在全新隔离 PostgreSQL 实例中恢复备份；比对用户、团队、供应商、模型、余额/退款、API Key、会话和审计对象数量及关键业务不变量。
3. 若找不到可信全库备份，仅将旧库/物理数据副本用于隔离环境中的数据抢救。恢复出的记录须标记为未验证，由业务负责人逐类确认后导入新库；不得把活库 `pg_dump` 或旧数据目录宣称为可信备份。
4. 目前已知的 2026-08-29 API Key SQL 不是全库恢复点，且其中凭据需要撤销，不可直接作为线上密钥恢复源。

数据库验收至少包括：外键与索引有效、关键表行数与备份清单相符、余额与退款对账、用户与团队归属核对、所有旧会话和用户 API Key 均失效、供应商及插件逐项复核。核验结果连同备份哈希异机归档。

### 6. 部署应用并切流

- 从可信 Git 源检出已审查提交；将本次 ZIP 校验与后端插件默认拒绝代码一起纳入新构建。构建机和制品需记录提交号与哈希。
- 不复制旧主机的 `config.json`、插件目录、`node_modules`、systemd 单元、cron/timer、SSH 配置或二进制。逐项重建配置并使用新凭据。
- 初始部署关闭所有插件，保持 `CR_TRUST_IN_PROCESS_PLUGINS` 未设置；需要插件时逐个审查源码和权限。
- 使用 Node.js 20 或更新版本安装依赖；当前锁文件的 `npm audit` 没有已知漏洞，但这不替代可信构建与制品校验。
- 先在隔离环境完成登录/2FA、供应商访问、数据库迁移、备份恢复、日志转发和出站限制验证，再由上游防火墙分阶段切入流量。
- 旧主机和原始磁盘在完成取证前保持隔离，只能在明确的回滚/取证窗口中访问；不能将旧应用进程直接作为回滚方案。

## 上线门槛

- 所有仍承载业务的受影响主机都从可信镜像重建，管理密钥、数据库口令和第三方凭据均已轮换。
- 恢复源、数据库核验报告和导入记录可追溯；无法证明完整性的记录已单独标注。
- 监听端口与公网暴露清单一致；SSH root 密码认证关闭；数据库不接受公网连接。
- CrewRouter 以低权限账号运行；未知插件关闭；异常登录、Web 服务派生 Shell、授权文件变更、陌生监听端口及非预期出站连接能异机告警。
- 可从新的离线备份实际恢复到隔离环境，并记录校验结果。

任一门槛未满足时，环境仍应标注为“恢复中/数据未验证”，不得宣称主机清洁或数据完整。
