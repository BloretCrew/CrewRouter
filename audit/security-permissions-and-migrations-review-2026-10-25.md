# 权限与启动迁移专项复核（2026-10-25）

本轮继续检查 API Key、Team 模型访问和启动时的数据写入。所有复现使用合成数据、依赖替身或全新私有 Unix socket PostgreSQL；没有读取生产 Key、调用真实上游、执行生产迁移或业务修库。以下代码缺陷不等于已证实的入侵利用路径。

## API Key 缓存不能替代有效期和撤销核验

旧 `validateApiKey` 在 60 秒缓存命中时只检查缓存中的启用状态，未重新核验当前 Key 是否存在、启用、到期或仍有拥有者。模型配置刷新虽然查询了 Key，却对缺失记录回退为空对象；本地缓存清理不能覆盖其他进程缓存、并发加载回填或自然到期。

现在每请求读取 Key 与拥有者关联，删除/拥有者消失返回 401，禁用返回 403，已到期（含等于到期时间）返回 401；无效时清理缓存，不回填、不更新使用时间。三个生成入口在命令、插件和 Fusion 分支之前再次核验并翻译受控认证错误，保留 OpenAI / Anthropic 响应格式。已通过检查的在途请求仍可能完成，不能把它描述为撤销正在执行的上游任务。

没有发现原地轮换同一 Key 行凭据的应用接口。本轮没有增加对直接 SQL 改写 `key_value` / `key_hash` 的缓存指纹比对；数据库被直接篡改仍超出应用缓存的可信边界。

## 对实际执行的模型行授权

旧授权查询把所有获准模型的本地 ID、alias、上游名合成允许集合；实际解析却先按全局本地 ID，再按别名匹配。合成场景中，用户获准模型 A 的 alias 等于另一 Team 专属模型 B 的本地 ID：既有绑定或 Fusion 预设中的 B 标识可通过允许集合检查，实际却解析到 B。重复 alias / upstream 名也有同类问题。

新增共享解析器，统一按本地 ID → 确定性 alias 顺序解析；Fusion 保留上游名回退。先得到具体模型对象，再只以它的本地 ID 检查 Team、模型及供应商启用状态，并将同一对象用于执行。OpenAI、Anthropic、Responses 三个入口及 Fusion 流式/非流式实际调用均接入；预检后目录变化也不能使执行借用其他同名模型的授权。计费元数据查询保留独立读取方式。

Fusion 入口同时在读取配置前拒绝缺失用户身份，流式执行明确使用需要权限的解析方式，避免 `undefined` 误入仅供计费元数据读取的分支。

## 启动迁移可能重复修正时间

旧时间迁移先查询标志，再逐表独立提交 `created_at + 8 hours`，最后独立写标志。真实函数在隔离库中复现：并发首启将 00:00 改成 16:00；第一张表已提交、第二张表失败后重试，会留下第一张表 16:00、第二张表 08:00，最后仍写成功标志。

现在使用同一独立连接及事务，取得迁移命名锁后重新检查原标志，两张表更新和标志原子提交，任何失败完整回滚并阻止此次启动。保留原标志名称，已有标志正常跳过；没有删除现场标志或自动对历史时间做反向修正。可信恢复时仍须确定源备份的时间语义，不能仅因缺少标志就认定所有记录都应加八小时。

## 模型历史回填会猜错已有身份

旧模型历史迁移按供应商和上游名连接模型后，直接以 `DISTINCT ON ... ORDER BY m.id` 选择结果，没有保留已经合法的本地 ID，也没有排除一对多歧义。隔离复现中，合法 `local-a` 因另一模型的上游名同名被改成 `local-b`；多候选的 `shared` 被任意归到字典序最前的模型；标志写入失败时改写已单独提交。

修复使用独立事务和迁移命名锁，保留同供应商的合法本地 ID；仅唯一上游匹配才转换，多候选或未匹配保留原值。改写、未解析计数和原迁移标志同事务提交。`unresolved` 只统计模型值、供应商值均非空的未解析记录，缺供应商记录仍原样保留。已有旧标志会跳过，不能自动修复过去已错写的记录；历史归属必须与可信备份/供应商账单核对。

## 启动个人 Team 与真实唯一约束

启动补建个人 Team 原先只插入 `user_teams`，没有同步 `users.team_id`；隔离真实函数顺序执行即可留下主归属为空、成员映射存在。预选用户后还可能与管理员分配交错。

现在每用户事务内锁用户、重新检查两份归属，再创建当前事务独有的个人 Team 并同时更新投影；已有归属保留，不选择默认 Team，不自动改写来源未知的不一致。投影写入失败会连同新 Team 回滚，并向启动抛错。另修正 `catch(e)` 内误抛 `err`，避免掩盖原错误。

复核发现前轮团队测试错误地使用了 `user_id` 单列主键，而仓库真实建表是 `UNIQUE(user_id, team_id)`。它掩盖了 `setUserTeam` 的 `ON CONFLICT(user_id)` 在真实结构中会报 `42P10` 的缺陷。现已按真实组合唯一键重建测试；辅助函数在锁定用户、删除旧映射后普通插入，无需引入新的唯一约束。前轮补丁尚未部署，没有证据表明现场执行过这条失败语句。
